## Goal
Wrap every database-backed test in a Postgres transaction that rolls back on completion. No test write ever commits. Eliminates state leaks, removes parallelism collisions, makes test data deterministic by construction, and replaces brittle `Date.now()` ID tricks with proper isolation.

## Why
While verifying HV-036, I observed one transient test failure across many runs. Investigation surfaced three real issues in the test architecture, not just one:

1. **State leaks between tests.** `afterEach` deletes only `user`; everything else relies on cascade. A failed test leaves orphan rows. A crashed process leaves orphan rows. Slowly contaminates the test DB.
2. **No isolation under parallel execution.** Vitest runs test files in parallel. `schema.test.ts` and `projects.test.ts` both hit the same Postgres instance. Today UUIDs prevent constraint violations — but the architecture *allows* collision; we're just not stepping on the rake.
3. **`Date.now()` and `randomUUID()` for unique IDs.** Test data depends on wall-clock and random sources. Determinism is a property tests should have *by construction*, not by hoping the values don't collide. The visible symptom is `installId: Date.now()` in two test files; the architectural problem is "test data shouldn't depend on non-deterministic sources."

The shallow fix (replace `Date.now()` with a counter) papers over symptom 3. The architectural fix solves all three at once: per-test transactional rollback. This is the industry-standard pattern for testing DB-backed code in Postgres — used by every serious ORM testing setup, scales from 10 tests to 10,000 with zero code changes, substrate-portable across Postgres/MySQL/SQLite.

This is also blocking HV-032 (CI). Without transactional isolation, CI's parallelism amplifies the latent flakiness — what's a 1-in-50 flake locally becomes a 1-in-5 flake under CI's higher concurrency. We don't want to install CI on top of brittle tests.

## Done when

### Test fixture installed

- New file `src/lib/test-db.ts` exporting a vitest fixture (or helper) that:
  - Begins a transaction on test start.
  - Returns a transactional `db` handle scoped to the test.
  - Forces rollback at test end (no commit ever).
- The pattern is documented in a top-of-file comment so future contributors know how it works.

### Existing tests migrated

- `src/db/schema.test.ts` uses the transactional fixture. `Date.now()` removed. `afterEach(db.delete(...))` removed (rollback handles it). Tests still pass 20/20.
- `src/lib/projects.test.ts` uses the transactional fixture. Same cleanup.
- `src/lib/access.test.ts` is unchanged (it mocks `@/db` entirely; no transaction needed) — but verify the migration doesn't accidentally affect it.

### Determinism enforced

- No `Date.now()`, `Math.random()`, or `Date()` in any test data. Replace with explicit constants where IDs are needed across tests.
- `randomUUID()` is acceptable for test isolation tokens (e.g., test user IDs) since collision probability is cryptographically zero — but document why it's allowed even though it's "non-deterministic."

### Documentation

- `CLAUDE.md` gets a "Testing rules" section: tests are transactional by default; no wall-clock or `Math.random()` in test data; `randomUUID` is allowed for unique tokens.
- Inline comment at top of `test-db.ts` explaining the rollback mechanism so future readers understand it's intentional.

### Verification

- `npm run test` passes 20/20 across **20 consecutive runs** (replaces the "ran twice and got 20/20" check that masked the flakiness in HV-036).
- `npm run test` with vitest's parallelism explicitly maxed (e.g., `--pool-options.threads.maxThreads=8`) still passes 20/20.
- A deliberately broken test (commit some bad data, expect query to find none → mutate the test to query for committed data) confirms rollback works — the data is invisible to the next test.

## Desired output
Tests are isolated by construction. No code path relies on cleanup running, no `Date.now()` arithmetic, no parallelism prayers. CI can crank up concurrency without flakiness; tests can be added by anyone without learning the "where do I put Date.now()" tribal knowledge.

## Success signals
- Zero observed flakes across CI's first 100 runs after this lands.
- Adding a new DB-backed test takes no special ID-generation ceremony — just `tx.insert(...)` with whatever values the test needs.
- A future ORM swap or DB migration doesn't require rewriting test setup; transactional rollback works on any transactional DB.

## Failure signals
- The transactional fixture is hard to use (boilerplate per test) — likely means the abstraction is wrong; iterate.
- Tests start running 5x slower because transaction overhead adds up — measure and optimize, possibly by sharing a connection pool across tests.
- Some test legitimately *needs* committed data (e.g., tests a background job that polls for new rows). Rare; if it happens, that test gets a separate non-rollback fixture and is documented as the exception.

## Tests
- The transactional fixture itself gets a meta-test: write data inside `withRollback`, verify it's gone after.
- All 20 existing tests pass under the new fixture.
- 20-consecutive-run check passes (vs. the previous 1-in-50 flake rate).

## How to test
1. Start with `src/db/schema.test.ts` — migrate it to the fixture first; smallest scope.
2. Run `npm run test` 20 times in a row. Should be 20/20 every time.
3. Migrate `src/lib/projects.test.ts`.
4. Run again 20 times.
5. Add the meta-test verifying rollback semantics (insert in test A → query for it in test B → not found).
6. Update `CLAUDE.md` with the rule.

## Notes
- Drizzle's `db.transaction(async (tx) => { ... })` callback commits if the callback resolves and rolls back if it throws. The trick is making the callback *resolve to the test* (so the test runs inside the tx) and then forcing rollback at the end. Common pattern: throw a sentinel `ROLLBACK` error from the callback, catch it outside.
- Existing helper patterns: see `vitest-postgres-rollback`, `pg_isolated_test`, or roll our own. Rolling our own is small (~30 lines) and avoids a dep — recommend that path.
- Out of scope: integration tests that intentionally test commit behavior (e.g., webhook idempotency across requests). Those would need a separate non-rollback fixture and are not currently in the test suite.
- Out of scope: SQLite/in-memory test DB. Real Postgres catches schema drift between Drizzle types and actual DB; we're keeping that fidelity.
- This is the long-term-correct fix per the substrate-vs-conventions framing: the *pattern* (per-test transactional isolation) is portable across Postgres, MySQL, SQLite, any future ORM. The shallow fix (counter instead of Date.now()) carries forward exactly nothing.

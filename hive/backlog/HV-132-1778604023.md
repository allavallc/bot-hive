## Goal

Expose the seat map on the read side (one endpoint) and render it on the kanban so the operator can scan colony state at a glance and watch shifts happen live.

## Concrete changes

- **`GET /api/bots/colony?colony=X`** — return `[{handle, seat, role, joined_at, last_heartbeat_at}, ...]` ordered by seat ascending, active rows only.
- **Kanban UI seat strip** — small horizontal strip at the top of the project board (or next to the existing swarm-health panel — see Notes on placement). One chip per seat: `seat N: <handle> (<role>)`. Empty colonies render a placeholder ("no bots active").
- **SSE subscriber** — the kanban page already has an SSE connection for ticket events. Add a handler for `bot.left` events: replace the colony seat strip's local state with `event.data.seat_map`.

## Done when

- [ ] `GET /api/bots/colony?colony=X` returns the live seat map in seat-ascending order
- [ ] Empty-colony case returns `[]` (not 404)
- [ ] Kanban renders the seat strip on page load using `/colony`
- [ ] When a bot calls `/leave`, the strip updates within ~1s for all open kanbans, no refresh needed
- [ ] The strip degrades gracefully if SSE disconnects (falls back to a re-fetch on reconnect)

## Notes

**Layout proposal needed before build.** Per the FS-027 convention ("UI changes need explicit visual approval before build"), the developer claiming this ticket must post a placement proposal in `hive/notes-to-humans/<bot>.log` and wait for explicit "go" from the operator before writing UI code. Two plausible homes: (a) top of the board, full-width strip above the column headers; (b) inside the existing swarm-health panel as a new subsection. The ticket does not pre-decide.

**Why `/colony` is its own endpoint, not bundled into `/whoami`.** `/whoami` returns one bot's view; `/colony` returns the whole map. The UI needs the latter; bots only need the former. Keeping them separate avoids over-fetching from the script path.

**Out of scope:**
- Per-bot detail drawer (clicking a seat chip) — file as follow-up if useful.
- Seat history / who-held-which-seat over time — historical view is a different feature (FS-004 territory).

**Risk.** The strip pulls colony name from the project context. If a project is associated with multiple colonies (currently it isn't, but the schema allows it), the strip needs a colony selector. Defer to a follow-up ticket if and when that comes up.

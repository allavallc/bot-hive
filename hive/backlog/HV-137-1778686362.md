## Goal

Remove the "Add a bot" button from the web UI. Replace with `scripts/add-bot.{sh,ps1}` — a CLI helper that does what the button did, run from the terminal.

## Why

Operators are in the terminal when they need to spawn a bot. The CLI version stays in flow; the button never did. Ripping the button out also simplifies the dashboard.

## Concrete changes

- New `scripts/add-bot.sh` (POSIX) and `scripts/add-bot.ps1` (PowerShell). Invocation: `./scripts/add-bot.{sh,ps1} <handle>`. Both perform, in order:
  1. Validate `<handle>` against `hive/handles.txt` (or accept arbitrary; spec it).
  2. `git worktree add worktrees/<handle> -b <handle>-work main`.
  3. Write `worktrees/<handle>/.bot-hive-identity` with `colony=<gh api user .login>` and `handle=<handle>`.
  4. Write `worktrees/<handle>/.bot-hive-kickoff` (one-shot kickoff marker — bootstrap deletes it).
  5. Print exact next-step instruction: `cd worktrees/<handle>` and `claude` (or codex/etc.) — the kickoff marker triggers auto-bootstrap.
- Remove the "Add a bot" button and its handler from the web UI (component + route + tests).
- Update `AGENTS.md`, `hive/bot-startup.md`, and `hive/HIVE.md` to reference the CLI flow. Drop button references.
- README (or equivalent at repo root) gains a short "Spawning a bot" section pointing at the CLI.

## Done when

- The CLI helpers exist on both platforms, behave identically, and produce a working worktree + identity + marker.
- The button is gone from the web UI; no orphaned routes/handlers.
- Docs updated so a new operator never reads about the button.
- A spawned bot from the CLI joins the colony cleanly: SSE handshake completes, role notice arrives, identity announced. Existing bots in the colony receive their role-change push.

## Desired output

Operator types `./scripts/add-bot.sh buzz`. Output: a worktree at `worktrees/buzz/`, identity + kickoff marker in place, plus one printed line saying what to do next. Operator opens a new terminal, `cd worktrees/buzz`, starts their agent. Bot bootstraps automatically.

## Success signals

- End-to-end spawn under 30 seconds, no web UI interaction.
- The CLI matches the prior button's behavior exactly (same identity shape, same marker semantics).
- Re-running with an existing handle errors clearly instead of corrupting the worktree.

## Failure signals

- CLI silently overwrites an existing worktree.
- Operator runs from inside a worktree by mistake — should refuse or warn.
- Docs still mention the button after this lands.
- The bash and PowerShell scripts drift in behavior.

## Tests

- Unit: invoking with a fresh handle creates all three artifacts; invoking with an existing handle fails with a clear message.
- Manual: `./scripts/add-bot.sh testbot`, open a new terminal in the worktree, start an agent, confirm it bootstraps and joins the colony.
- Manual: verify `worktrees/<handle>` is on its own branch (`<handle>-work`), not `main`.
- Manual: confirm the existing bot in the operator's main checkout receives the role-change SSE push when the new bot joins.

## Notes

Per HV-129, kickoff triggers are: operator types `start the hive` OR `.bot-hive-kickoff` marker file exists. The CLI uses the marker-file trigger so the new agent auto-starts without the operator typing anything in chat.

Worktree path convention is `worktrees/<handle>/` per existing AGENTS.md / `hive/HIVE.md`.

After this ships, the dashboard's "See Bot Team" modal (HV-132) still shows the active team — that's fine. It just no longer offers spawning.

## Goal
Load the GitHub App private key from the `GITHUB_APP_PRIVATE_KEY` env var contents directly, with the existing `GITHUB_APP_PRIVATE_KEY_PATH` filesystem path as a fallback for local dev convenience.

## Why
Render — and serverless / containerised hosts in general — don't have a stable writable filesystem to drop a `.pem` file in. Env vars are the canonical pattern. Keeping the file-path fallback means local dev keeps working with the existing `~/.gcloud-keys`-style layout.

## Done when
- `src/lib/github.ts` `loadPrivateKey()` reads `GITHUB_APP_PRIVATE_KEY` first (newline-decoded if needed), falls back to `GITHUB_APP_PRIVATE_KEY_PATH`, throws if neither is set.
- Local dev still works with the existing `.env` setup (file path).
- Prod can be configured by pasting the PEM contents into the Render env-var UI as `GITHUB_APP_PRIVATE_KEY` (literal newlines or `\n` escapes both supported).
- `.env.example` updated with both options documented.

## Desired output
A single `loadPrivateKey()` call that just works whether running locally with a key file or on Render with the contents in an env var.

## Success signals
- `npm run dev` still authenticates as the GitHub App without changes to local `.env`.
- A prod env with only `GITHUB_APP_PRIVATE_KEY` set (no path) still mints installation tokens.

## Failure signals
- The env var contents have escaped newlines (`\\n`) instead of real newlines and Octokit fails to parse the PEM. Helper must accept either form and normalise.
- Both env vars are unset → throw with a helpful error pointing the user at `.env.example`.

## Tests
- Manual: with only `GITHUB_APP_PRIVATE_KEY` set (path unset), confirm `appOctokit()` works.
- Manual: with only `GITHUB_APP_PRIVATE_KEY_PATH` set (env unset), confirm it still works.
- Manual: with both set, env var wins.

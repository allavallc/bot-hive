## Goal

Add the lifecycle write endpoints and the server-side reclamation that together keep the seat sheet honest when bots exit (cleanly or not).

## Concrete changes

- **`POST /api/bots/heartbeat`** — input `{colony, handle}`. Bump `last_heartbeat_at = now()`. **No-op for offline rows** (don't accidentally reactivate from a stale background process). 200 always (idempotent).
- **`POST /api/bots/leave`** — input `{colony, handle}`. Inside the same per-colony advisory lock as HV-130:
  1. `SELECT seat FROM bots WHERE colony=:c AND handle=:h AND status='active' FOR UPDATE` → `departing_seat`. 404 if not found.
  2. `UPDATE bots SET status='offline' WHERE id=:row_id`.
  3. `UPDATE bots SET seat = seat - 1 WHERE colony=:c AND seat > :departing_seat AND status='active'`.
  4. Publish `bot.left` SSE event with the new seat map.
- **`bot.left` SSE event** — extends the platform's existing SSE channel. Payload: `{colony, departed: {handle, seat}, seat_map: [{handle, seat, role}, ...]}`. Routes through the same project SSE the swarm panel already subscribes to.
- **Reclaim job** — APScheduler (or equivalent in-process scheduler) running every 60s inside the Flask app. Query: `SELECT colony, handle FROM bots WHERE status='active' AND last_heartbeat_at < now() - interval '15 minutes'`. For each match, run the same transaction as `/leave`. From the survivor's POV a timeout is indistinguishable from a manual sign-off.

## Done when

- [ ] Heartbeat against an active row bumps `last_heartbeat_at`
- [ ] Heartbeat against an offline row is a no-op (status stays `offline`, no row created)
- [ ] `/leave` marks the row offline and decrements `seat` for everyone with `seat > departing_seat`
- [ ] After `/leave`, the partial unique index allows the next `/join` in the same colony to take the now-vacant top seat
- [ ] Renumber-with-gaps test: 4 bots, bot 2 leaves, bots 3 and 4 become 2 and 3 respectively; no orphan rows; index still satisfied
- [ ] `bot.left` event fires on the project SSE channel with the correct payload
- [ ] Reclaim job marks idle rows offline within 60s of the 15-minute threshold
- [ ] Reclaim job emits the same `bot.left` event for timeout-driven exits
- [ ] Reclaim job is idempotent: running twice on the same idle row is a no-op the second time
- [ ] Integration tests for all six scenarios above

## Notes

**Why APScheduler in-process and not a separate cron.** Render Free tier doesn't ship a cron primitive cleanly; running it in-process keeps deployment a single service. The job is tiny (one query, possibly zero updates) so it adds negligible load.

**SSE channel reuse.** Bot Hive already streams ticket-lifecycle events via project SSE. `bot.left` rides the same channel with a distinct `event:` name so existing subscribers ignore it harmlessly. The kanban UI in HV-132 adds the subscriber.

**Heartbeat-to-offline-row behavior is deliberate.** If a bot's background heartbeat process keeps pinging after `/leave` (cleanup race), we don't want to silently undo the leave. The bot's startup procedure handles legit return-to-active explicitly via `/join` — see HV-133.

**Out of scope for this ticket:**
- `GET /colony` and the UI subscriber — HV-132.
- Client-side heartbeat process — HV-133.

**Risk.** The 60s reclaim sweep + 15-minute timeout means a crashed bot keeps a seat for up to 15 min in the worst case. That's intentional (avoids reclaiming a genuinely slow heartbeat round-trip). If we ever see "phantom seats >15 min after a crash" in practice, tune the timeout; don't shorten the sweep interval (that just adds DB load).

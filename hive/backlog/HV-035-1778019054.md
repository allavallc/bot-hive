## Goal
A permanent staging environment on Render — a second Web Service tracking a `staging` branch, with its own database, OAuth App, and GitHub App. PRs land first on `staging`, get tested on `bot-hive-staging.onrender.com`, then promote to `main` (which deploys to prod). Main only ever contains tested code.

## Why
Current model: every PR auto-merges to `main` on green CI; `main` deploys to prod. With zero users that's fine — broken pushes are recoverable in minutes and nobody notices. The moment there are real users, the "test on prod" trade becomes real downtime risk.

A permanent staging environment is the standard fix: source code lands on `staging` first, gets tested on a public-but-non-production URL, then is promoted to `main` after sign-off. Rollback is `revert PR on staging` rather than `revert PR on prod`.

## Done when

- A `staging` branch exists at `origin/staging`, kept up to date with `main` plus any in-flight PRs targeted for promotion.
- A second Render Web Service (`bot-hive-staging`) tracking the `staging` branch, separate from prod.
- Staging Postgres — Neon free tier (no expiration, 500MB, fits easily). Separate from prod DB; never shares state.
- Staging OAuth App on GitHub: callback URL = `https://bot-hive-staging.onrender.com/api/auth/callback/github`. New client ID + secret in staging env.
- Staging GitHub App: separate App ID, separate webhook secret, separate private key. Webhook URL = `https://bot-hive-staging.onrender.com/api/github/webhook`.
- `docs/STAGING_SETUP.md` documenting the provisioning step-by-step (analogous to `docs/BRANCH_PROTECTION.md`).
- `render.yaml` (or equivalent config) updated for the staging service.
- The promotion workflow documented in `AGENTS.md` and `HIVE.md`: PR target = `staging`, then a separate `staging → main` PR after acceptance.

## Desired output
A bot opens a PR. CI passes on staging branch's PR. Bot auto-merges to staging. Staging redeploys (~2 min). Human (or test-bot) verifies on staging URL. On accept, bot opens promotion PR (`staging → main`). Auto-merges. Main redeploys to prod. Total wall-clock: ~5-10 min from PR open to prod, with a real test gate in between.

## Success signals
- A bug shipped to staging gets caught before reaching prod, at least once.
- Prod has zero "we shipped a regression we caught immediately" incidents in the first 30 days after staging is live.
- The staging env stays free or near-free on Render's Pro plan.

## Failure signals
- Promotion gets skipped under time pressure ("just push to main, staging is fine"); becomes a habit; the safety rail erodes.
- Staging drifts from prod (different schema, different env vars, stale data) so testing on staging stops predicting prod behavior.
- Render free-tier cold starts on staging make testing unbearable, pushing humans to skip the staging step.

## Tests
- Manual: open a PR with a deliberate breakage. Confirm staging deploys, bug is visible there, never reaches prod.
- Manual: open a no-op PR. Confirm full cycle (PR → staging deploy → accept → promotion PR → main deploy) takes <15 min wall clock.

## How to test
1. Walk through `docs/STAGING_SETUP.md` from a clean state (or as a thought experiment).
2. After provisioning, open a test PR with a visible cosmetic change (e.g., title text). Promote through staging. Verify prod gets the change.
3. Open a test PR with a deliberate visible bug. Promote to staging. Verify the bug is visible there. Reject. Confirm prod doesn't change.

## Notes

### Deferred per user direction (2026-05-05)

User explicitly said to defer this until there are real users. Pre-launch, prod is zero-cost to break (no one is watching), and the operational complexity of running two environments isn't earning anything. Pick this up before any real launch — almost certainly Q2 or later.

### Cost picture
- Staging Web Service: free on Render (allow it to sleep when idle; ~30s cold start is acceptable for testing).
- Staging Postgres: $0 on Neon free tier.
- Two extra GitHub Apps: free.
- Total: $0/mo as long as Render's free Web Service tier is still in place on the Pro workspace.

### Worst case
If Render free-tier instance types get phased out on Pro workspaces (a real risk based on recent plan changes), staging compute moves to a $7/mo Starter Web Service. Still cheap; not a blocker.

### Out of scope
- Per-PR Render preview environments (already rejected — single OAuth callback URL constraint makes them impractical).
- Multi-region staging.
- Load testing infrastructure on staging.

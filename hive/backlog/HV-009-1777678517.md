## Goal
Let users drag tickets inside `backlog/` to set the order bots pick them in.

## Why
P0/P1/P2 is too coarse to express "do this one next." A draggable ordinal closes the gap without leaving the kanban.

## Done when
- Bot Hive frontmatter accepts `order: <int>` (ascending; ties fall back to `priority` then file mtime).
- Bot Hive GitHub App has `Contents: Write`; a drop commits one-file frontmatter diff via the installation token.
- Bot adapters that read tickets from this format respect `order` when selecting from `backlog/`.
- Drag is enabled only on the `backlog/` column; other columns reject drag.
- UI updates optimistically; SSE rebroadcast confirms the persisted order.

## Desired output
Reordering in the UI changes the bot's next pick on its next cycle.

## Success signals
- Concurrent user reorder + bot move-out-of-backlog land as separate commits without file conflict.
- Reorder commits are small (single ticket, single field).

## Failure signals
- Every drag emits a commit (no debounce); repo churns.
- Bot Hive ships `order` writes before any bot reads it; UI lies.

## Tests
- Unit: `order` parses as int; missing → `Infinity`.
- Manual: reorder three tickets; confirm bot picks in new order on next cycle.
- Manual: simultaneous user drag + bot pick; both commits land cleanly.

## Notes
- Phase 2 polish. Bot Hive owns the format; the only cost of adding `order` is updating the parser and any bot adapter that writes tickets.
- Out of scope: cross-column drag, bulk reorder, edit-in-place.

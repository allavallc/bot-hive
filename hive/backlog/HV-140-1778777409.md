## Goal
`cancel()` on `ReadableStream` is not reliably called in Next.js App Router (Node.js runtime) when a client socket closes — `req.signal` is the reliable path. Without this fix, a bot shutting down never triggers `disconnectBot()`, so surviving bots never receive their updated `your-role` events.

## Why
When a bot shuts down, surviving bots must receive `your-role` events within seconds so they can recheck their consolidated roles. Today this silently fails because `cleanup()` — which schedules `disconnectBot()` and the peer pushes — never fires.

## Done when
- `req.signal.addEventListener('abort', ...)` is wired in `src/app/api/bots/stream/route.ts`
- `cleanup` nulls itself on first call so double-firing (`cancel()` + `req.signal`) is a no-op
- The comment "Single-instance Render Free assumed" is removed (we're on Starter)

## Desired output
When a bot's `stream.ps1` is killed, the server reliably runs `disconnectBot()` after the grace period and pushes `your-role` to affected peers.

## Success signals
- Surviving bots' `.bot-hive.log` shows `[stream] event: your-role` within ~16s of a peer shutting down
- `[BOT-HIVE] Role changed:` appears on the next operator prompt for affected survivors

## Failure signals
- Surviving bots never log a `your-role` event after a peer shuts down
- Dead bot's row stays `status=active` in the `bots` table indefinitely

## Tests
- Shut down one bot, wait 16s, confirm `.bot-hive.log` on a surviving bot shows `your-role` event
- Confirm dead bot's DB row is `status=offline` after the grace period

## Notes
Root cause: in Next.js App Router (Node.js runtime), `ReadableStream.cancel()` fires when the *consumer* cancels, not necessarily when the underlying TCP socket closes. `req.signal` aborts on socket close and is the correct hook. Adding `{ once: true }` prevents a stale listener if the stream outlives the request object. The `cleanup = null` guard prevents double-execution if both paths fire.

## Goal

Make tester approval an explicit server-side gate before work can be treated as merge-ready.

## Why

Multi-agent output is not trustworthy if code can move from coder completion directly to merge with only self-reporting. The tester role needs an enforceable approval record, with CI as the final mechanical gate.

## Done when

- A tester approval/rejection record exists for a ticket or PR after review.
- Coder ready-for-review events route work to the tester role.
- Rejections route back to the coder with a reason.
- Merge-ready state is unavailable without tester approval and passing CI status.
- Existing human accept/reject flows remain unchanged for user-facing review.

## Desired output

Coder work must pass a separate tester decision before it is eligible to ship.

## Success signals

- A PR/ticket without tester approval is visibly blocked.
- A tester rejection returns actionable feedback to the coder.

## Failure signals

- A coder can self-approve by posting a ready event.
- CI green alone is enough to present work as ready to merge.

## Tests

- Unit tests for approval/rejection state transitions.
- Route tests or helper tests for merge-ready eligibility.
- Manual test with one approved and one rejected ticket.

## How to test

- Simulate ready-for-review, rejection, rework, approval, and CI-passing states.

## Notes

This ticket should not implement GitHub branch protection itself unless the server-side eligibility model needs a GitHub status check to be testable.

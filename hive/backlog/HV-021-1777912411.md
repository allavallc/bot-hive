## Goal
Surface a visible difference in the Bot Hive UI between platform operators (Anthony et al.) and regular Bot Hive users — admins see admin-only affordances (admin nav, ops dashboard); regular users see only their normal experience.

## Why
As Bot Hive grows beyond a single user, the operator needs to do platform-level work — debug user issues, see the full project list, audit billing, ban abusive users — that should never be visible to regular customers. Today there's no notion of "admin" anywhere in the schema or UI. A signed-in operator is indistinguishable from any other signed-in user.

## Done when
- An admin identification mechanism exists (decision: a `role` column on `user` with values `'user' | 'admin'`, default `'user'`; OR an env-list `ADMIN_USER_IDS` checked at runtime — pick one at draft time).
- Admin sign-in produces a visible "Admin" badge in the top nav (or a label after the user's name).
- An admin-only nav link exists; regular users don't see it.
- The destination page (e.g. `/admin`) is gated — non-admins get a 404 or "Not authorized" response.
- A reusable `isAdmin(userId): Promise<boolean>` helper in `src/lib/access.ts` (or a new `src/lib/roles.ts`) so the same check works in middleware, server components, and API routes.

## Desired output
When Anthony signs in, the nav shows an "Admin" badge and an admin menu link. When a regular user signs in, they see no admin affordances. Visiting `/admin` while signed in as a regular user returns a 404.

## Success signals
- Two test users — one admin, one regular — see the correct UI on each load.
- Admin URLs return 404 for non-admins.
- The role helper is mocked easily in tests (mirrors the `userHasRepoAccess` pattern from HV-018).

## Failure signals
- A regular user accidentally sees admin-only data — security issue, treat as a bug.
- Admin badge persists for a user whose role was just demoted (cache lag).
- A new operator added later isn't picked up because the gate hardcoded their ID.

## Tests
- Vitest: `isAdmin` returns the correct value for each role.
- Vitest: admin route handler returns 404 for non-admins.
- Manual: sign in as admin → admin nav visible. Sign in as non-admin → no admin nav.

## How to test
1. Locally, set your own user record's role to `'admin'` (via a SQL script or env var, depending on the chosen mechanism).
2. Sign in. Confirm the "Admin" badge appears in the nav.
3. Sign out, sign in with a second test account. Confirm no admin badge.
4. From the second account, visit `/admin` directly. Confirm 404.
5. Sign back in as admin. Confirm the admin page loads.

## Notes
- Out of scope: the actual admin tools (ops dashboard, user list, project audit, impersonation, etc.). Those are follow-up tickets that build on the `isAdmin` foundation.
- Out of scope: any concept of project-level admin — that's already handled by GitHub repo permissions per FST-003.
- Recommendation: `role` column on `user` (with a Drizzle migration), values `'user' | 'admin'`, default `'user'`. Cleaner than env-list, scales to more roles later, makes it trivial to grant/revoke without redeploy.
- Probably wants its own feature set ("Operator / admin tooling") once a second admin ticket appears. For now, Standalone.

## Goal
Add a "Bot handle" filter to the board (alongside the existing Priority and Feature-set filters). Selecting a handle shows only tickets where `Assigned to:` matches that handle. Lets a human answer "what is nectar doing?" or "show me everything tern has touched" with one click.

## Why
The existing filters cover **what** (priority, feature set). They don't cover **who**. As the swarm grows, "who's doing what" becomes the most useful slice — especially for the human reviewing work or debugging coordination issues.

Bot handles are already on every ticket card (per HV-036/HV-041) and in the audit trail. Adding a filter is a small UI addition that turns existing data into a navigation primitive.

## Done when

- The board's filter row gets a third dropdown: **Bot handle**.
- The dropdown is populated dynamically — distinct values of `Assigned to:` (extracting the handle, ignoring the optional `(model-id)` suffix) across all tickets in the project.
- Selecting a handle filters the visible tickets to only those assigned to it.
- "All" option resets the filter (default state).
- The filter persists in the URL query string (e.g., `?handle=nectar`) like the existing Priority/Feature-set filters.
- The filter combines with existing filters via AND (e.g., Priority=High + Handle=nectar shows only High-priority tickets assigned to nectar).
- Empty state when filter matches nothing: "No tickets assigned to <handle> in this project."
- typecheck + lint + tests + build all clean.

## Desired output
A user opens the board, clicks the Bot-handle filter, picks `nectar` — sees only tickets where I worked. Picks `tern` — sees CC2's tickets. Quick context-switch between agent views.

## Success signals
- Humans use the filter to answer "what is X bot up to?" without grep'ing the file system.
- Filter combines naturally with Priority and Feature-set (each agent's High-priority tickets in FS-007).

## Failure signals
- The handle list is too long / too many handles per project (mitigation: dropdown order by recency or activity count).
- Filter shows tickets assigned to a handle that's no longer active (mitigation: that's correct behavior — historical tickets keep their original assignment).

## Tests
- Manual: open the board, click handle filter, pick nectar. Confirm only nectar's tickets show.
- Manual: combine Priority + Handle. Confirm AND behavior.
- Manual: handle filter URL persistence (refresh keeps the filter).

## How to test

4. Combine with Priority filter. Confirm AND.

## Notes
- Uses existing `extractHandle()` helper from HV-036's badge implementation.
- Out of scope: filter by model-id (e.g., "show all claude-opus-4-7 work"). Handles are per-session; model is per-trailer. Different filter, different ticket if needed.
- Out of scope: showing handles' avatars/colors in the dropdown (text-only is fine).
- Out of scope: a "my tickets" shortcut for the currently-signed-in user (would need a separate concept of "is this human associated with handle X" — the human signs in as a GitHub user, not a bot handle).

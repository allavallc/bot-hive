## Goal

Migrate operator-managed settings into a `platform_settings` DB table editable from the admin dashboard. First migration target is `SWARM_HEALTH_CRON_SECRET`; the table should be designed to absorb future operator settings as they appear (no per-setting schema migrations).

## Concrete UX

- New admin dashboard section: **Settings**. Lists every key in `platform_settings` with current value (secrets masked, copy-to-clipboard for the unmasked value), last-updated-by, last-updated-at.
- Edit affordance per row: inline edit → save → audit row written.
- Two value types in v1: `string` (plain) and `secret` (masked in the UI; stored encrypted at rest if Render Postgres doesn't already encrypt; revealed only on explicit click).

## Schema sketch

```
platform_settings (
  key text primary key,
  value text not null,
  type text not null check (type in ('string','secret')),
  description text,
  updated_at timestamptz not null default now(),
  updated_by uuid references users(id)
)
```

## Migration approach

- Code reads `getPlatformSetting('SWARM_HEALTH_CRON_SECRET')` instead of `process.env.SWARM_HEALTH_CRON_SECRET`.
- The helper falls back to env var IF the DB row doesn't exist (zero-downtime migration: env var stays as the bootstrap value until the operator sets the DB row, then DB wins).
- Once all operators have moved to the DB row, the env var can be removed from Render — no code change needed.

## Goal
On prod, an open `/projects/[id]` board page should visibly re-render in real time when a `hive/` commit hits the connected repo — confirming that webhook → broadcast → SSE → client refresh works end-to-end on Render.

## Why
During HV-024 testing, a push to bot-hive moved a ticket on the prod board, but the user reported "didn't see it move but it did move." The new state appeared on next view rather than animating in via SSE. Either the SSE connection isn't being established, the broadcast isn't firing, or the client isn't re-rendering on the event. All are real bugs worth diagnosing.

## Done when
- Open `/projects/[id]` in a foreground browser tab on prod.
- Push a `hive/` commit (any ticket move or content edit).
- The board visibly updates within ~10s — ticket moves columns, body changes refresh — without manual reload.
- Render logs show: `POST /api/github/webhook` received, `[broadcast]` event fired, SSE clients notified.
- Browser dev tools (Network → EventSource) show the SSE connection alive and receiving the `project-changed` event.

## Desired output
The "live" in "live kanban" actually works on prod.

## Success signals
- Visible UI animation/refresh on push within 10s.
- SSE event count increments in browser dev tools.

## Failure signals
- SSE connection drops on Render's reverse proxy (long-lived connection issue — Render *should* support this but verify).
- Broadcast fires but client never gets the message (`X-Accel-Buffering: no` header may need attention).
- Client gets the event but doesn't re-render (SWR cache, query invalidation logic).

## Tests
- Manual on prod (open board + push). Watch Render logs + browser EventSource panel.
- Possibly add a Vitest for `subscribe()` / `broadcast()` interaction if the bug turns out to be in those primitives.

## How to test
1. Open `https://bot-hive-j0ax.onrender.com/projects/[your-bot-hive-project-id]` in a foreground tab. Open browser dev tools → Network → filter by "EventSource" or "stream".
2. Confirm the `/api/projects/[id]/stream` connection is open (status 200, kept alive).
3. From a separate terminal, push a `hive/` commit to the bot-hive repo.
4. Watch the board: should update within ~10s.
5. In dev tools, the EventSource should show new messages received.
6. In Render logs, should see `POST /api/github/webhook` then a broadcast log line.

## Notes
- Render natively supports long-lived SSE connections; this isn't a host-level "doesn't work" issue. More likely a header / cache / re-render bug.
- Out of scope: rewriting the SSE primitive. This ticket is verification + small fix only.
- If the issue is timing (eventual consistency feels acceptable), document it and move on.

### Code audit (kestrel, 2026-05-06)

Walked the full path from webhook receipt to client re-render. No code-level bugs found; all the boxes the original report would suggest are already checked off:

| Hop | File | Status |
|---|---|---|
| HMAC verify + delivery-id passthrough | `src/app/api/github/webhook/route.ts` | ✓ verifies signature, forwards `x-github-delivery` to handler |
| Per-project lock + dedupe by delivery-id | `src/lib/webhook.ts` `handlePushEvent` | ✓ `withProjectLock` serializes; `webhookDeliveries` table dedupes |
| Sync DB then broadcast | `src/lib/webhook.ts:56-57` | ✓ `initialSync(projectId)` resolves before `broadcast({type: "project-changed", projectId})` |
| Broadcast → subscriber fan-out | `src/lib/broadcast.ts` | ✓ swallows individual subscriber throws (`try/catch`), so one bad client doesn't block others |
| SSE controller writes event | `src/app/api/projects/[id]/stream/route.ts` | ✓ `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform`, **`X-Accel-Buffering: no`** (defeats reverse-proxy buffering on Render), 30s keepalive comment line |
| Client EventSource + refetch | `src/app/projects/[id]/board.client.tsx` `useEffect` | ✓ parses event JSON, refetches `/api/projects/[id]/tickets` on `project-changed`, reconciles state, animates moves |

So: the original report ("didn't see it move but it did move") most likely cause is one of these *operational* conditions, not a code bug:

1. **Browser tab was backgrounded** — most browsers throttle/suspend EventSource processing on hidden tabs. The next foreground or `visibilitychange` triggers a state pull which sees the latest snapshot, hence "the new state appeared on next view."
2. **EventSource auto-reconnect after a transient disconnect ate the event** — `EventSource` retries automatically, but events fired during the gap are lost (we don't replay project-changed events on reconnect, only signal events do via `getSignals` on the `/signals/stream` route). If Render briefly closed the connection while the webhook fired, that event is gone.
3. **Render's free/starter plan went to sleep** — first request after sleep wakes the instance; webhook may have been processed by a cold instance with no live SSE subscribers.

Recommended next steps if the user-facing symptom recurs:

- (Code, optional) Add a "replay last project-changed timestamp on connect" so reconnecting clients can detect they missed an event and refetch once. Cheap; not strictly needed if (1) is the root cause.
- (Operational) Confirm the prod plan keeps the instance warm.

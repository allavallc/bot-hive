## Goal
Replace the in-process `botStreams` Map with Postgres LISTEN/NOTIFY so peer `your-role` events reach bots on any server instance, not just the one that received the disconnect.

## Why
Render Starter uses zero-downtime deploys — two instances run simultaneously during every deploy. The `botStreams` Map lives in Node.js process memory. A bot on instance A can't push to a bot on instance B; `pushPeer()` silently finds nothing in the local Map and returns. Result: surviving bots never learn their new role after a peer leaves during a deploy window.

## Done when
- `src/lib/bot-registry.ts` manages the in-process `Map<connectionId, send>` and exports `registerStream`, `unregisterStream`, `deliverToConnection`
- `src/lib/bot-notify.ts` wires a dedicated Postgres LISTEN connection at startup; exports `publishPeerPush()` which calls `pg_notify('bot_push', ...)`; on receive calls `deliverToConnection()`
- `stream/route.ts` uses `registerStream`/`unregisterStream` instead of the local Map and `publishPeerPush` instead of `pushPeer`
- No new npm dependencies (uses existing `postgres` package)

## Desired output
After any bot shuts down — even during a rolling deploy — surviving bots on any instance receive `your-role` within ~16s and `check-role.ps1` surfaces the role change on the next operator prompt.

## Success signals
- Surviving bots' `.bot-hive.log` shows `[stream] event: your-role` within ~16s of a peer shutdown, regardless of which Render instance each bot is connected to
- `bots` table row for the departed bot is `status=offline` after the grace period

## Failure signals
- `[bot-notify] pg_notify failed` appears in Render logs
- `[bot-notify] LISTEN setup failed` on startup

## Tests
- Shut down one bot, wait 16s, confirm `.bot-hive.log` on surviving bots shows `your-role`
- (Harder to test locally) Two-instance behavior verified by deploy observation

## Notes
No new npm dependency — `postgres` (postgres.js) is already in `dependencies` and supports `sql.listen(channel, callback)` natively with auto-reconnect. A dedicated `postgres` client (separate from the query pool) is used for LISTEN to avoid tying up pool connections with a persistent open channel. The main pool is used for NOTIFY via `db.execute(sql\`SELECT pg_notify(...)\`)`.

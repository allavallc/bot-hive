## Goal
Add vitest coverage for the parts of the signal channel that ship without tests today: the POST `/api/projects/[id]/signals` endpoint, the GET `/api/projects/[id]/signals/stream` SSE route, and the `broadcast.ts` pub/sub. `signal-buffer.ts` already has full coverage — this ticket extends to the rest of FS-011.

## Why
HV-047, HV-048, and HV-055 shipped the channel + the swarm panel + the pending-transition badge with zero tests on the HTTP routes or the broadcast module. The buffer module is tested, but every code path between an HTTP request and `addSignal()` is unverified. Any future change to validation rules, auth, or broadcast wiring can silently break the swarm panel and the pending-transition badge with no test failure to catch it.

## Done when

### POST /api/projects/[id]/signals
- 401 when no session
- 404 when session exists but user has no access to the project
- 400 for missing/empty body, invalid signal type, missing message, message > 500 chars, refs array > 10 entries, refs entry > 50 chars, refs entry empty
- 201 on valid payload, with the new signal returned in the response
- Side effects on success: `addSignal(projectId, signal)` is called once with a signal containing `user: <session.user.name>`; `broadcast({ type: "signal", projectId, signal })` is called once

### GET /api/projects/[id]/signals/stream
- 401 when no session
- 404 when session exists but no project access
- 200 on success with `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform`, `Connection: keep-alive`
- Replay: signals already in the buffer for that projectId are emitted as `data:` frames in order before any keepalive
- Subscribe: when `broadcast({ type: "signal", projectId, signal })` fires, the stream emits a matching `data:` frame
- Filter: signals broadcast for a *different* projectId are not forwarded to this stream

### broadcast.ts
- `subscribe(projectId, callback)` returns an unsubscribe function
- Multiple subscribers all fire on `broadcast(...)` for their projectId
- `unsubscribe()` removes only that subscriber, not others
- Subscribers for a different projectId do not fire

### Verification
- typecheck + lint + build clean
- vitest goes from 28 passing to ≥ ~45 passing (rough — depends on how granular each `test(...)` is; aim for one test per assertion above)
- No flaky tests — SSE timing tests should poll with a short timeout (~50ms), not sleep

## Out of scope
- E2E tests that drive the swarm panel browser-side (`swarm-panel.client.tsx`) — separate ticket if useful later.
- Tests for `EventSource` client behavior — hard to mock cleanly in vitest; defer until we have a reason to.
- Load testing the SSE channel.

## Notes
- The existing `signal-buffer.test.ts` is the closest pattern to follow for buffer-level tests. The route tests should mock `auth.api.getSession` and `getProjectForUser` rather than hit the real DB; the test-db fixture is overkill for these.
- `broadcast.ts` uses a small in-process pub/sub (`EventEmitter` or hand-rolled). Tests should assert against the public API only.
- For the SSE route, a single test that opens the `Response`, reads `body.getReader()` for the first chunk, and verifies it includes a `data:` line covering replay is enough. Subscribe-to-broadcast can be tested by calling `broadcast()` after the reader is open and verifying the next chunk arrives.

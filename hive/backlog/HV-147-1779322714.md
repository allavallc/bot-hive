## What

Instrument the repo-connect flow with structured server-side logs so we can trace one attempt across these stages:

1. User reaches `/projects/new`
2. Bot Hive resolves the GitHub App slug / install URL
3. GitHub redirects back to `/projects/install/callback`
4. Bot Hive validates session + `installation_id`
5. Bot Hive lists installation repositories
6. Bot Hive scaffolds `hive/` if needed
7. Bot Hive upserts the `projects` row
8. Bot Hive runs initial sync
9. Bot Hive redirects to `/dashboard`

Use a stable per-attempt correlation id carried through the flow where possible, and emit one final success/failure summary event with the first failing stage, if any.

## Why

Right now repo-connect support is too blind. We have partial callback error logs, but not enough to answer:

- Did the user make it to GitHub?
- Did GitHub send us back an `installation_id`?
- Did we fail before repo listing, during scaffolding, or during sync?
- Was this an owner/collaborator/permission problem, missing server credentials, or an app-side bug?

Without that trace, every failure becomes a manual interview and reproduction exercise.

## Done when

- [ ] `/projects/new` logs a structured "connect flow started" event once the page has a valid session and before rendering the install button
- [ ] Failure to resolve the GitHub App/install URL logs a structured error event with stage = `resolve-install-url`
- [ ] `/projects/install/callback` logs structured stage events for session check, installation id parse, installation repo listing, per-repo scaffold attempt, project upsert, initial sync, and final redirect
- [ ] Each event includes enough correlation fields to be actionable without leaking secrets (for example: user id, installation id, github repo full name when known, request path, stage, result, error class/message)
- [ ] A single connect attempt can be followed in local dev logs from start to finish using the correlation id
- [ ] Known expected failures (missing session, invalid installation id, GitHub API failure, scaffold failure, sync failure) log clearly and do not silently disappear
- [ ] No secrets are logged: never dump OAuth secrets, GitHub private keys, full request headers, cookies, or raw tokens

## Desired output

A coder bot should land:

- a small helper for structured repo-connect logging (or a clearly scoped pattern if a helper is overkill)
- instrumentation in `src/app/projects/new/page.tsx`
- instrumentation in `src/app/projects/install/callback/route.ts`
- any tiny supporting changes needed to propagate a correlation id across the flow safely
- a short note in code comments or docs explaining how to read the emitted events in local dev

## How to test

1. Start local dev server and watch the terminal logs.
2. Run a successful connect flow and verify ordered events appear from `connect flow started` through final redirect.
3. Trigger at least two failure modes and verify the logs clearly show the first failing stage:
   - invalid or missing `installation_id`
   - temporary breakage of GitHub App credentials/path, or a mocked GitHub API failure
4. Confirm logs include correlation id + useful identifiers but no secrets.
5. Confirm existing repo-connect behavior still works after instrumentation.

## Notes

- Prefer structured objects over ad-hoc strings so later log aggregation is possible.
- Keep the first version lightweight: terminal/server logs are enough. This ticket is about visibility, not analytics infrastructure.
- Distinguish expected product-state failures (permission mismatch, collaborator without install rights, invalid callback input) from code faults.
- If one connect attempt can touch multiple repos in the callback, preserve both an overall attempt id and per-repo stage context.
- Out of scope: changing the user-facing UX or copy for connect failures. This ticket is observability first so later UX tickets can be driven by real evidence.

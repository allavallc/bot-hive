## Goal
When a human clicks Accept or Reject on an in-review card, the card moves to the destination column **immediately** (within ~1s of the click) — not after the full deploy cycle (~10 min). The pending-transition banner stays visible to indicate the move is still in flight server-side. When the actual SSE ticket-state refresh confirms the underlying file move, the banner clears and the card's "real" state takes over with no visual jump.

## Why
Today's flow:
- 0s: user clicks Reject → orange banner appears on the card → card stays in **In-Review**
- ~10 min: PR + CI + Render redeploy + DB sync land → card finally moves to **In-Progress**

The 10-minute lag between the user's click and the card moving is unacceptable UX. The user can already see "the rejection registered" via the banner, but the card sitting in In-Review for 10 min reads as "stuck." Meanwhile the user can't act on the same card again, and the board's columns feel out of sync with the user's intent.

Structural fix: the board's column-bucketing already has access to `pendingTransitions` (set by HV-055). Just use it. If a ticket has `pendingTransition === "rejected"`, render in In-Progress. If `"approved"`, render in Done. The banner already explains *why* it's there ahead of the deploy.

## Done when

### Logic change in `board.client.tsx`

In the column-bucketing loop (around line 207 today), check for a pending-transition entry per ticket:

```ts
function effectiveState(ticket: Ticket, pending: { kind: "approved" | "rejected" } | undefined): string {
  if (!pending) return ticket.state;
  if (ticket.state !== "in-review") return ticket.state; // safety; pending only applies from in-review
  return pending.kind === "approved" ? "done" : "in-progress";
}
```

Use `effectiveState` when bucketing tickets into columns. The actual `ticket.state` is unchanged on the data model; only the visual placement shifts.

### Pending-transition banner (already shipped in HV-055/072)

Keeps doing what it does. The banner is the user's signal that the card has moved optimistically and is waiting for the server.

### Cleanup (already shipped in HV-055)

When the SSE ticket-refresh shows the ticket has actually moved (`ticket.state !== "in-review"`), the pending-transition entry is cleared. After that, `effectiveState` returns `ticket.state`, and the card sits in its real column with no banner. Should be a no-op visual change because the optimistic placement and the real placement match.

### Edge cases
- Two users open the board, user A clicks Reject. User B sees the card move to In-Progress with the banner within ~1s (via SSE signal stream). Same UX both sides.
- User clicks Reject, deploy fails (rare). The banner has a 10-min hard timeout (HV-055) — when it clears, `effectiveState` falls back to `ticket.state` which is still "in-review." Card jumps back to In-Review. Could surface a "deploy failed" toast in a follow-up; out of scope here.
- User refreshes the page during the wait. Server-side state is unchanged (still in-review). The optimistic state is per-tab, so the refresh shows the card in In-Review again until the deploy lands. Acceptable for v1; HV-076's webhook-driven progress states will give richer signal.

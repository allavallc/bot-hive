## Goal
Stand up Bot Hive on Render — a Web Service running the Next.js app + a managed Postgres — with the schema migrated and a working public URL.

## Why
Bot Hive runs only on a dev laptop today. Without a public URL nothing works that involves a second user (HV-019 multi-account test), a deployed webhook (no more smee), or showing the product to anyone who isn't sitting next to Anthony.

## Done when
- A `render.yaml` (Render Blueprint) at the repo root defining the Web Service + Postgres database.
- Build command: `npm ci && npm run build`. Start command: `npm run db:migrate && npm run start`.
- All required env vars set in the Render dashboard:
  - `DATABASE_URL` (auto-injected from the linked Postgres)
  - `BETTER_AUTH_URL` (the Render URL or custom domain)
  - `BETTER_AUTH_SECRET` (rotate from local; new random 32-byte base64)
  - `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`
  - `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY` (full PEM contents, per HV-022)
  - `GITHUB_APP_WEBHOOK_SECRET`
  - `SMTP_USER`, `SMTP_PASS` (only if the contact form should work in prod; otherwise leave unset and it returns the disabled error)
- First deploy succeeds; the public URL serves `/login` with a 200.
- Drizzle migrations applied to the prod DB (verify `__drizzle_migrations` table has rows for `0000` and `0001`).
- Webhook + OAuth URLs *not* yet pointed at prod (that's HV-024).

## Desired output
`https://bot-hive.onrender.com` (or similar) loads the login page in <2s after warm-up. The prod Postgres has the schema migrated and is empty of user data.

## Success signals
- `curl https://<prod-url>/login` returns HTTP 200.
- `psql <prod-DATABASE_URL> -c "\dt"` shows all expected tables.
- Render logs show the Next.js server bound and listening, no startup errors.

## Failure signals
- Build fails because `next build` hits a lint or typecheck error that didn't surface locally — fix and push.
- `db:migrate` fails on first run if the Postgres credentials are wrong or the network is locked down — should fail loudly, retry once env is fixed.
- SSE endpoint returns 502 in prod — Render shouldn't have this issue (long connections supported), but if it does, that's a host-level config bug to investigate.

## Tests
- Manual: after deploy, hit `/login` from a browser. Confirm page renders.
- Manual: connect to prod Postgres directly, run a `SELECT * FROM "user"` — should return empty.
- No automated tests — this ticket is platform configuration.

## How to test
1. Push the branch with `render.yaml` to GitHub.
2. In Render dashboard: New → Blueprint → select the bot-hive repo → confirm the YAML is detected.
3. Provision the Postgres database first; wait for it to come up.
4. Provision the Web Service; let the first build run. Watch the deploy logs.
5. Once green, open the assigned `*.onrender.com` URL. Confirm the login page renders.
6. Don't try to sign in yet — the GitHub OAuth callback URL still points at `localhost:3000`. That's HV-024.

## Notes
- Use Render's "Free" tier for the Web Service to start; upgrade if cold-start latency is intolerable.
- Postgres on Render: smallest paid tier ($7/mo) — free tier expires after 90 days, not worth it for a real app.
- Out of scope: custom domain, CDN, Sentry, rate limiting — separate tickets.
- Render's `render.yaml` Blueprint syntax docs: https://render.com/docs/blueprint-spec
- `db:migrate` runs at server start. If it fails, the whole boot fails — that's the right behaviour for migrations.

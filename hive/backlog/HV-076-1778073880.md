## Goal
Enrich the pending-transition banner (HV-055/072) with concrete real-time progress from GitHub during the 10-min in-flight window. Instead of a static `Rejected — pending merge`, the banner ticks through `PR opened` → `CI running` → `CI ✓ merging` → `merged, deploying` → (clears). The user sees forward motion every minute or two, eliminating the "is this stuck?" sense.

## Why
HV-075 makes the card move to its destination column within 1s — the worst UX problem. But the user still waits 10 min for the underlying state to land, and a static banner during that wait reads as "stuck." GitHub already emits real-time events for every stage; surfacing them on the banner turns the wait into a visible progress indicator.

## Done when

### Webhook handler extension

`/api/github/webhook` today receives `push` events. Extend to also handle:
- `pull_request` (action ∈ `opened`, `closed`, `reopened`)
- `check_suite` (action ∈ `requested`, `in_progress`, `completed` with `conclusion`)
- `deployment_status` (state ∈ `pending`, `success`, `failure`)

For each event, the handler:
1. Identifies the PR's branch name (from the event payload).
2. Looks up the in-flight ticket whose pending-transition signal references this PR. (Implementation: tickets are linked to PRs via the branch naming convention — the accept/reject route already creates branches like `accept-<hvId>-<timestamp>` or `reject-<hvId>-<timestamp>`. The handler parses the hvId out of the branch name.)
3. Publishes a `progress` signal on the SSE channel: `{ type: "progress", refs: [hvId], stage: <stage>, message: <human-readable> }`.

### New signal type

`signal-buffer.ts` adds `"progress"` to the `SignalType` union. The signal carries:
```ts
{
  type: "progress";
  refs: [hvId];
  stage: "pr-opened" | "ci-running" | "ci-passed" | "ci-failed" | "merged" | "deploying" | "deployed";
  message: string; // e.g. "PR #67 opened", "CI ✓ merging"
}
```

### Board renders the stage

`board.client.tsx`:
- Listens to `progress` signals on the existing SSE stream subscription.
- Maintains `pendingProgress: Map<hvId, { stage, message, at: number }>`.
- The pending-transition banner reads the latest progress message:
  - Default: `Rejected — pending merge` (HV-055/072 baseline).
  - With progress: `Rejected — PR #67 opened` / `Rejected — CI running...` / `Rejected — merged, deploying` / etc.

### Stage → message mapping

| Stage | Banner text (rejected) | Banner text (approved) |
|---|---|---|
| `pr-opened` | `Rejected — PR #N opened` | `Approved — PR #N opened` |
| `ci-running` | `Rejected — CI running` | `Approved — CI running` |
| `ci-passed` | `Rejected — CI ✓ merging` | `Approved — CI ✓ merging` |
| `ci-failed` | `Rejected — CI failed` (red) | `Approved — CI failed` (red) |
| `merged` | `Rejected — merged, deploying` | `Approved — merged, deploying` |
| `deploying` | `Rejected — deploying` | `Approved — deploying` |
| `deployed` | (banner clears, real state takes over) | (same) |

### CI failure path

If a stage of `ci-failed` arrives, the banner stays visible (in red) until either:
- The user re-runs / re-opens the PR (CI re-runs, banner reverts to `ci-running`)
- The 10-min hard timeout (HV-055) kicks in and clears it

Don't auto-roll-back the optimistic column placement on CI fail — the user sees the failed banner and decides what to do.

### Webhook subscription

The Bot Hive GitHub App's webhook subscription needs `pull_request`, `check_suite`, `deployment_status` events enabled in addition to `push`. Document the change in `docs/DEPLOY.md` (operator runbook) so adopters know to update their installation.

## Out of scope
- Live duration counter (`Rejected — CI running, 1m 23s`). Could be a small follow-up; v1 is the discrete stages.
- Linking the banner text to the GitHub PR URL. The detail panel already has the URL; the banner stays plain text.
- Render-specific deploy events. Render emits `deployment_status` events through GitHub for connected services — that's the integration point. No direct Render API call needed.

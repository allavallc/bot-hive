## Goal
A "feature-set view" toggle on the board that re-organizes cards: top-level grouping is **by feature set** (each FS as a swim lane or section), with each FS's tickets inside it grouped by state (or shown as a compact progress bar). Complements — doesn't replace — today's "by state" view (Backlog / In-Progress / In-Review / Done columns).

## Why
Today the board is a Jira-style state kanban. That's good for "what's the swarm doing right now" but bad for "how is FS-007 progressing as a body of work?" or "which feature sets are stalled?"

A feature-set view answers different questions:
- Which FSes are in flight, near-done, or stalled?
- For FS-X, what % is done? What's still in backlog?
- What's the next likely thing to land per FS?

The state view stays as the default (it's the moment-to-moment lens). The FS view is the strategic lens.

The exact UX needs design — punt the visual decisions to implementation time. The first version can be simple (one section per FS, with each section showing its tickets in compact form colored by state).

## Done when

### Toggle

- A view-mode toggle on the board header: **State** (current default) / **Feature set**.
- Toggle persists in URL query param (e.g., `?view=fs`).

### Feature-set view layout (first cut)

- One section per feature set with the FS title as the section header.
- Inside each section, show the FS's tickets — could be:
  - **Option A:** mini-board (4 columns: backlog/in-progress/in-review/done) per FS, each section is small.
  - **Option B:** flat list of tickets sorted by state, with a state badge on each card.
  - **Option C:** progress bar showing N done / M total + an expandable list.
  - To be decided during implementation. Option B is probably the simplest first cut.
- Tickets that aren't assigned to any FS go in a "Standalone" section at the bottom.

### Existing filters still apply

- Priority, handle, FS filters from HV-057 etc. still work in this view (filtering reduces what shows in each section).
- The FS-filter dropdown becomes redundant in FS-view (each section is already an FS) — hide it when in FS-view.

### Sort + collapse

- FSes are sorted by their NNN number (numerical order).
- Each FS section is collapsible; collapsed state remembered per-user (localStorage).
- Empty FSes (no tickets in scope) are hidden by default.

### Verification

- typecheck + lint + tests + build all clean.
- Manual: switch to FS view; confirm sections appear; confirm filters still work.

## Desired output
A user clicks "Feature set" on the board view toggle. The board re-renders as sections — one per FS. Each section shows the FS's tickets and a sense of progress. A user reviewing strategic progress sees what FS-007 looks like as a whole, what's still owed in FS-005, etc.

## Success signals
- Humans use the FS view to answer strategic questions (which FSes are stalled, what's near-done).
- Switching between State and FS views feels fast and intuitive.

## Failure signals
- The FS view becomes the only useful view; users abandon the State view. (Mitigation: that's actually fine; State view stays for swarm-level monitoring.)
- The FS view is too dense (many FSes, many tickets) — overwhelming without scrolling.

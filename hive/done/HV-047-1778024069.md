## Goal
Server-side foundation for the real-time channel. Bots POST signals to a project's channel; everyone with an open SSE connection receives them within ~100ms. No persistence beyond an in-memory ring buffer of the last ~100 signals per project.

## Why
The board already has SSE infrastructure for ticket-state updates (`/api/projects/[id]/stream`). This adds a peer endpoint specifically for ephemeral bot-to-bot signaling, decoupled from the durable webhook-driven flow.

## Done when

### API surface

- **`POST /api/projects/[id]/signals`** — publish a signal.
  - Auth: same `userHasRepoAccess` gate as other project routes.
  - Body: `{ type: SignalType, message: string, refs?: string[] }` where `type` is one of `claim | done | blocked | question | note | handoff` (extend later if needed; gate on this enum at the server).
  - Server enriches with: `id` (UUID), `timestamp` (ISO), `bot` (handle, from `BOT_HIVE_HANDLE` header or session), `userId` (if posted by a human via the board UI, taken from session).
  - Server writes to the project's in-memory ring buffer (last 100 signals, oldest evicted).
  - Server fans out to all open SSE connections for that project.
  - Returns the enriched signal as JSON.
- **`GET /api/projects/[id]/signals/stream`** — SSE stream.
  - Auth: same gate.
  - On connect: replays the current ring buffer (up to last 100 signals) so a freshly-opened board sees recent context.
  - Streams new signals as they arrive.

### Storage

- Per-project in-memory ring buffer (`Map<projectId, Signal[]>`). No DB. Process restart wipes it — that's fine; signals are ephemeral by design.
- Hard cap: 100 signals per project. Oldest dropped when the buffer is full.
- A signal expires after 1 hour (lazy eviction on read). Keeps the buffer fresh and stops stale "I'm starting HV-X" signals from confusing later sessions.

### Verification

- Vitest: POST returns 200 + the enriched signal; subsequent GET `/stream` includes it in the replay.
- Vitest: POST without auth (no session, no GitHub repo access) returns 403.
- Manual: open the board, open the network tab, POST a signal via curl with the right auth cookie — confirm the SSE stream emits the new signal in real time.

## Desired output
A bot can publish a signal in ~50ms; any other bot or human with the SSE stream open receives it in ~100ms. Sub-second latency, no git involvement.

## Success signals
- Latency from POST → SSE delivery: <200ms locally, <500ms on prod.
- A board UI built on top (HV-048) feels responsive — signals appear without perceivable delay.
- The buffer doesn't grow unbounded across many sessions.

## Failure signals
- A bot's POST blocks for >1s (suggests SSE fan-out is synchronous when it should be async).
- The ring buffer leaks memory under load (look for projects with 1000+ signals queued).
- A human types in the board's input box (HV-048) and the message takes >1s to appear for other watchers.

## Tests
- Vitest unit: ring-buffer eviction + 1-hour TTL behavior.
- Vitest integration: POST + GET cycle with mocked auth.
- Manual: end-to-end on prod.

## How to test
1. Land HV-047, deploy.
2. Open the board on prod. Open the browser's network tab → look for the `/signals/stream` SSE connection.
3. From a separate terminal, `curl -X POST .../api/projects/<id>/signals -H 'Cookie: <session>' -d '{...}'`.
4. Watch the network tab — the SSE stream should emit the new signal within ~500ms.
5. Confirm the signal isn't persisted: restart the server (`npm run dev` cycle), reopen — the signal is gone.

## Notes
- **Why in-memory not Redis?** Pre-launch, single-instance Render service. In-memory is sufficient. When we go multi-instance (or want signal persistence across restarts), swap to Redis pub/sub — same API, swap implementation. Substrate-portable.
- **Why not just append to events.log?** events.log is durable — bots write there for state transitions (ticket lifecycle events) that should survive forever. Signals are ephemeral chatter — pushing every "I'm thinking about X" into events.log would bloat the audit trail with noise.
- **Auth model:** project-scoped. Anyone with GitHub repo access can publish + subscribe. Same gate as the rest of the project routes. No per-bot identity verification beyond the handle in the payload — handles are advisory, not security.
- Out of scope: cross-project channels (a global #lobby), DMs between specific bots, signal threading/replies, persistent pinned messages. All can be follow-up tickets if the v1 proves useful.
- Out of scope: rate limiting. Add if abuse appears; not pre-launch.

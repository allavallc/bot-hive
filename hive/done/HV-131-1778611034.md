## Goal

Add the lifecycle write endpoints, the in-process broadcast event for live UI updates, and the lazy server-side reclamation that together keep the seat sheet honest when bots exit — cleanly or not.

## Concrete changes

- **`src/lib/broadcast.ts`** — extend `BroadcastEvent` (lines 11–20) with two new union variants:
  ```ts
  | { type: "bot-left"; projectId: string; colony: string; departed: { handle: string; seat: number }; seatMap: SeatMapEntry[] }
  | { type: "bot-joined"; projectId: string; colony: string; joined: { handle: string; seat: number }; seatMap: SeatMapEntry[] }
  ```
  Add a `SeatMapEntry` type: `{ handle: string; seat: number; role: string }`.
- **`src/lib/seats.ts`** — extend with:
  - `markOffline(db: DbHandle, projectId: string, colony: string, handle: string)` → inside an advisory lock, finds the active row, sets status='offline', returns `departing_seat` (null if no active row).
  - `renumberAfter(db: DbHandle, projectId: string, colony: string, departingSeat: number)` → `UPDATE bots SET seat = seat - 1 WHERE project_id = $1 AND colony = $2 AND seat > $3 AND status = 'active'`.
  - `sweepStale(db: DbHandle, projectId: string, colony: string, threshold: Duration = '15 minutes')` → returns array of `{ handle, departingSeat }` rows that were marked offline; runs the same advisory lock + renumber per row. Called from `/join`, `/whoami`, `/colony`.
  - `seatMap(db: DbHandle, projectId: string, colony: string)` → returns `SeatMapEntry[]` for active rows in seat order. Used by routes that emit broadcast events.
- **`src/app/api/bots/heartbeat/route.ts`** — new POST handler. Body: `{ repo_full_name, colony, handle }`. Resolves project, then:
  ```ts
  await db.update(bots).set({ lastHeartbeatAt: new Date() })
    .where(and(eq(bots.projectId, projectId), eq(bots.colony, colony), eq(bots.handle, handle), eq(bots.status, 'active')));
  ```
  Returns `{ ok: true }` regardless of whether a row was updated (offline rows silently no-op).
- **`src/app/api/bots/leave/route.ts`** — new POST handler. Body: `{ repo_full_name, colony, handle }`. Inside `db.transaction`:
  1. Acquire `pg_advisory_xact_lock(hashtext(projectId || ':' || colony))`.
  2. Call `markOffline(tx, projectId, colony, handle)` → `departingSeat`. If null, return 404.
  3. Call `renumberAfter(tx, projectId, colony, departingSeat)`.
  4. Call `seatMap(tx, projectId, colony)` for the post-renumber state.
  5. After commit: `broadcast({ type: "bot-left", projectId, colony, departed: { handle, seat: departingSeat }, seatMap })`.
  6. Return `{ ok: true, departed: { handle, seat: departingSeat }, seat_map: seatMap }`.
- **Sweep-on-request integration** — modify HV-130's `/join` and `/whoami` to call `sweepStale` before their main logic (inside the same transaction). For each row swept, emit a `bot-left` broadcast event (so the UI sees timeout-driven departures the same as manual sign-offs).
- **Also broadcast on `/join` success** — `/join` emits `bot-joined` after its transaction commits so the kanban UI updates live when a new bot arrives.
- **Tests** — `src/app/api/bots/heartbeat/route.test.ts`, `src/app/api/bots/leave/route.test.ts`, `src/lib/seats.test.ts` extended. Test cases: heartbeat-active bumps, heartbeat-offline is no-op, leave marks + renumbers + broadcasts, sweep marks stale rows + renumbers + broadcasts (use Vitest fake timers + `db.update(bots).set({ lastHeartbeatAt: ... })` to backdate). Verify broadcast was called via a spy or by subscribing in-test.

## Notes

**Why sweep-on-request instead of a cron.** Per `docs/architecture.md`, Next.js has no in-process scheduler; the existing cron pattern (`src/app/api/health/cron/route.ts`) requires an external scheduler that is not currently declared in `render.yaml`. Adding the external cron is net-new infrastructure for marginal benefit — colonies with no active bots have no consumers asking about their state, so the dead-seat doesn't matter until someone asks, and when they ask, the sweep runs. A follow-up ticket can add a Bearer-protected cron route later if dashboards need proactive cleanup.

**Why broadcast inside the sweep.** Without the broadcast, the kanban shows stale seats until the next render-from-DB. With it, the operator's view updates within the SSE roundtrip — which is the whole point of giving bot lifecycle a real-time surface. The broadcast is in-process (per `docs/architecture.md`); Render Free is single-instance today, so this works.

**Why `broadcast` and not a new endpoint.** `src/lib/broadcast.ts` already exists, is keyed by `projectId`, already powers the kanban's SSE at `src/app/api/projects/[id]/stream/route.ts`. The new event types ride that channel for free. No new SSE infrastructure required.

**Heartbeat-to-offline-row is deliberately a no-op.** If a bot's background process keeps pinging after `/leave` was called (cleanup race), we do not want to silently undo the leave. The bot's startup flow handles legit return-to-active explicitly via `/join` — see HV-133.

**Out of scope:**
- `GET /colony` and the UI subscriber — HV-132.
- Client-side heartbeat script — HV-133.

**Risk.** Sweep adds a small DB cost to every `/whoami`/`/join`/`/colony` request. For a colony with N active bots, it's one indexed `SELECT ... WHERE last_heartbeat_at < now() - interval` (worst case zero rows). Negligible.

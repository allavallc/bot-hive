## Goal
Restructure the `projects` table so each `(installId, githubRepo)` has exactly one row, with `billingOwnerId` naming who pays.

## Why
The current unique key permits one project row per (owner, repo, install) tuple — same repo connected by two users yields two rows, duplicating sync work and breaking shared boards. Under derived membership the project IS the shared resource; `billingOwnerId` is metadata about who pays, not who can see.

## Done when
- New Drizzle migration: rename `owner_id` → `billing_owner_id`; drop `projects_owner_repo_install_unique`; add unique on `(install_id, github_repo)`; drop `projects_owner_idx`, add equivalent on `billing_owner_id`.
- `src/db/schema.ts` matches.
- HV-002 constraint tests adapted: legacy ownerId-based uniqueness check replaced by `(installId, githubRepo)` uniqueness.
- `npm run typecheck` clean. The rename surfaces in 5+ files; touch only the rename — auth-logic changes belong to HV-019.

## Desired output
A schema where `(install_id, github_repo)` is the unique key and `billing_owner_id` points at the user who pays.

## Success signals
- Migration applies cleanly on a fresh DB.
- New constraint test passes; existing tests pass after rename.

## Failure signals
- Migration fails if duplicate `(installId, githubRepo)` rows exist pre-migration. Should fail loudly, not silently coalesce. (No real data exists today.)
- Drizzle TS drift breaks `tsc`.

## Tests
- Vitest: insert two projects with same `(installId, githubRepo)` → second fails on unique violation.
- Vitest: insert two projects with same `billingOwnerId` but different repos → both succeed.
- Existing HV-002 tests adapted to use `billingOwnerId`.

## Notes
- No backfill SQL needed (no production data).
- Cascade-delete on `billing_owner_id → user.id` retained. Footgun risk: deleting the billing user's account drops the project even with other collaborators. HV-020 mitigates by letting collaborators take over before that happens. Revisit cascade if it becomes a real issue.
- Out of scope: lock-when-unpaid, plan validation. FST-005.

## Resolution
- `src/db/schema.ts`: column `ownerId` → `billingOwnerId`, dropped `ownerRepoInstallUnique`, added `installRepoUnique` on `(installId, githubRepo)`, dropped `ownerIdx` + redundant `installRepoIdx`, added `billingOwnerIdx`.
- Migration `drizzle/0001_billing_owner_rename.sql` hand-written using `ALTER TABLE ... RENAME COLUMN` so existing rows survive. Snapshot + journal updated in sync.
- Mechanical rename in 6 callsites: `dashboard/page.tsx`, `projects/[id]/page.tsx`, `api/projects/[id]/tickets/route.ts`, `api/projects/[id]/stream/route.ts`, `projects/install/callback/route.ts` (×2). Logic unchanged — auth-logic swap belongs to HV-019.
- `schema.test.ts`: existing test updated to use `billingOwnerId`; two new tests added asserting `(installId, githubRepo)` uniqueness collides and that one user can own multiple distinct repos.
- Verification: `npm run typecheck`, `npm run lint`, `npm run test` (4/4 pass), `npm run db:generate` reports no further schema diff (schema, snapshot, DB all aligned).
- Drizzle Kit's `generate` prompted interactively for rename-vs-recreate disambiguation — couldn't be fed via piped stdin on Windows. Hand-writing the SQL + snapshot was faster than fighting the prompt and produced an identical result.

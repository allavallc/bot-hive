## Note — what happened
The v1 panel shipped as specified (SSE consumer, human composer, type-based icons, fixed sidebar, persisted toggle). After it landed, it became clear that **no bot actually read the messages humans typed into the composer** — it was theater. The `/api/projects/[id]/signals` channel duplicated the existing webhook → broadcast wiring on `hive/events.log`, and the bot-token flow needed for humans/bots to publish there was a setup-hassle the user explicitly rejected ("this is a fucking pain").

PR #111 ripped out the duplicate channel (signals API, bot tokens, signal-buffer, presence.log) and refactored the panel to a read-only viewer of `events.log` — which every bot already writes to as part of normal work. The composer was removed in that pass.

Bringing the composer back as something **actually wired to bots** is captured in FS-015 (human↔bot comm). The architecture there is straightforward: session-cookie-authenticated POST that appends a `note-to-<agent-id>` line to events.log, which bots see on session start.

So: the work for HV-048 shipped, was iterated on, and the panel is on the board today as a read-only swarm view. The composer chunk lives in FS-015's future scope.

## Goal
Add a panel to the live board that renders the real-time signal stream from HV-047. Humans on the board see bot-to-bot chatter as it happens; humans can also type into the panel to publish their own signals. The panel makes the swarm observable.

## Why
HV-047 builds the API; the API is invisible without UI. Without UI, bots can talk to each other but humans can't see the conversation. The panel is the "window into the swarm" — humans glance at it to know what's happening, type into it to participate.

## Done when

### Panel placement and behavior

- A new panel on `/projects/[id]` board page. Sidebar (right edge, ~320px wide) on desktop; collapsible drawer on mobile.
- Panel title: "Swarm" (or similar — short, no jargon).
- Panel renders the SSE stream from HV-047's `GET /api/projects/[id]/signals/stream`.
- Initial render shows the ring-buffer replay (last ~100 signals); thereafter live appends as they arrive.
- Each signal renders as: `<bot-handle (colored)> · <type-icon> · <message> · <ago>` on one line.
- Type-based color/icon: `claim` = blue arrow, `done` = green check, `blocked` = red stop, `question` = yellow ?, `note` = grey, `handoff` = purple arrow. (Final palette decided during implementation.)
- Newest at the bottom, autoscroll unless the user has scrolled up (sticky-scroll pattern).

### Human input

- A small text input at the bottom of the panel: "Type a note to the swarm…"
- Enter publishes a `note`-type signal via `POST /api/projects/[id]/signals`.
- The published signal appears in the stream (the SSE delivers it back to the same client) within ~200ms.
- Author of human-published signals: the user's GitHub handle (from session), not a bot handle.

### Accessibility

- Panel can be toggled (show/hide) via a button on the board header.
- Toggle state persists in localStorage so it survives reload.
- Keyboard-navigable: Tab cycles into the panel; arrow keys scroll; Esc returns focus to the board.
- Color contrast meets WCAG AA on all signal types.

### Verification

- Manual: open the board, send a signal from another tab via curl (or another bot); the panel renders it in real time.
- Manual: type a note, hit Enter; appears in the panel; visible to a second open board on a second machine.
- Manual: toggle the panel off, reload, confirm it stays off.

## Desired output
A human on the board sees bots claiming work, finishing work, asking questions, and helping each other in real time. Looking at the panel for 30 seconds gives a clear sense of what the swarm is doing right now.

## Success signals
- Humans report "I can tell what the bots are up to without asking."
- Bots' signals visibly bracket their work (claim → progress notes → done) so the human can spot stalls.
- The panel feels like a chat room scoped to the project — readable and inviting, not noisy.

## Failure signals
- The panel is visually noisy (too many signals, too dense) and humans hide it permanently.
- Latency feels slow (>1s from POST to panel-rendered).
- The panel breaks the board layout on small screens.

## Tests
- Manual end-to-end as in Verification.
- Visual sanity check: signal types are visually distinct without being garish.

## How to test
1. Land HV-047 + HV-048 + a connected agent that publishes signals (HV-049's docs unblock that).
2. Open the board on prod. Confirm the panel is visible (or toggle it on).
3. Have a bot session somewhere POST a signal. Confirm it appears in the panel within ~500ms.
4. Type a note in the input. Confirm it publishes, appears in the panel, and is visible from a second open board.

## Notes
- Out of scope: signal filtering / search. Add if the panel grows past usable.
- Out of scope: emoji reactions, replies, threads. Single-line ephemeral signals only.
- Out of scope: signal persistence across page reloads beyond what the ring buffer (HV-047) gives. The ring buffer's 100-signal replay covers the typical reload case.
- The panel is both a coordination tool AND a transparency tool. Keeping it visible-by-default trades signal-to-noise (more visible) for surveillance (humans can see all chatter). The per-project scope keeps it bounded.

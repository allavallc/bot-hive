## Goal
Process GitHub `push` webhooks: verify HMAC, dedupe deliveries, update `tickets`/`features` for changed `hive/` files, broadcast a project-changed event.

## Why
Without a webhook handler the board only reflects state at install time. Live updates are the whole point of the product.

## Done when
- `POST /api/github/webhook` verifies `X-Hub-Signature-256` against `GITHUB_APP_WEBHOOK_SECRET`; mismatch → 401 silently.
- `X-GitHub-Delivery` is checked against `webhook_deliveries`; seen → 200 fast-return.
- For `push` events: resolve project by installation+repo; for each commit, look at `added`/`modified`/`removed` filtered to `hive/`; refetch contents at HEAD SHA via Contents API; upsert/delete in DB; update `sync_state.last_sha`.
- After successful DB write, broadcast a project-changed event to SSE subscribers (HV-007) and **only then** insert into `webhook_deliveries`.
- `Installation` and `Installation repositories` events at minimum log + 200; full handling deferred.

## Desired output
Push a commit moving a ticket file → DB reflects the move within 10s → board (HV-007) updates without manual refresh. Replaying the same delivery via curl is a no-op.

## Success signals
- HMAC verification rejects forged requests in unit tests.
- A re-delivery from the GitHub UI produces zero new rows.

## Failure signals
- `webhook_deliveries` insert before DB upsert → re-delivery skipped while DB is stale.
- Concurrent deliveries for the same project race the `last_sha` update.
- A 5xx from Contents API leaves partial state and 500s the webhook (GitHub keeps retrying for ~24h — fine, but log it).

## Tests
- Unit: HMAC verifier accepts a known-good payload and rejects a tampered one.
- Unit: replay of the same `delivery_id` early-returns 200 without DB writes.
- Manual: push add/modify/delete on a fixture repo; observe DB diff.
- Manual: replay a captured delivery via curl after a successful run; confirm no new rows.

## Notes
- Order matters: dedupe → verify → fetch → upsert → broadcast → record delivery. Recording last keeps re-deliveries useful when an upstream step errors.
- Webhook payloads can lie about `removed` for renames; treat rename as delete + add at HEAD content.
- Out of scope: full handling of `Installation` events (auto-disconnect on uninstall) — Phase 2.

## Resolution
- 4 files: `src/lib/webhook.ts`, `src/lib/broadcast.ts`, `src/app/api/github/webhook/route.ts`, plus a one-line export of `getApp` from `src/lib/github.ts`.
- **Sync strategy:** whole-folder refetch via `initialSync(projectId)` instead of per-commit-diff. Existing transactional sweep handles edits/deletes/renames uniformly. Trade ~2 extra API calls per push for zero edge-case code.
- **Multi-tenant fan-out:** `handlePushEvent` finds all `projects` rows matching `(install_id, github_repo)` and runs sync per project. Per-project dedup via `(project_id, delivery_id)` PK so the same delivery records independently per project.
- **Concurrent delivery race:** in-memory `withProjectLock` mutex per `projectId` — second concurrent webhook awaits the first. Phase 1 single-instance, this works. Phase 3 distributed deploy needs Postgres advisory locks.
- **HMAC verify:** reuses `App.webhooks` from `@octokit/app` (the App is already constructed with the webhook secret in `getApp`). One source of truth for the secret.
- **Order locked:** verify → ping-fast-return → parse → per-project (lock → dedup-check → sync → broadcast → record-delivery). Per-project errors caught + logged; one project's failure doesn't block siblings.
- **Broadcast layer (`src/lib/broadcast.ts`)** is in-memory `Map<projectId, Set<subscriber>>`. HV-007's SSE endpoint will subscribe.
- `Installation` and `Installation repositories`: log + 200, deferred to Phase 2.
- `ping` event: returns `{pong: true}` so GitHub's webhook setup test passes.
- Unit tests (HMAC tampered, replay no-op) deferred to HV-010 (Vitest not installed).

## Goal
Every PR to `main` runs typecheck, lint, tests, and build automatically in GitHub Actions. CI is the safety rail that lets bots self-merge their PRs without humans reviewing every change — green CI means the code at least compiles and passes existing tests.

## Why
Without CI, "branch + PR" gives source-code isolation but no enforcement. A bot could open a PR with broken types, lint errors, or failing tests; a second bot could merge it; main is broken; deploy breaks. CI fixes that by gating merge on green status checks. Combined with branch protection (HV-033), it makes parallel bot work genuinely safe — a bot literally cannot merge broken code.

## Done when
- New file `.github/workflows/ci.yml` triggered on `pull_request` (and `push` to main as a backstop).
- Job runs on `ubuntu-latest`, Node 20 (matches local dev).
- A `postgres:16` service container is brought up; `DATABASE_URL` env var points at it.
- Steps in order: `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test`, `npm run build`.
- Migrations run before tests (so the DB schema matches what tests expect): `npm run db:migrate` against the service container DB.
- The CI job appears as a status check on every PR (named `ci` so HV-033 can reference it in branch protection).
- The CI workflow itself is delivered via a feature branch + PR (dogfoods the new workflow that HV-031 documents).
- After merge, a fresh PR opened by a bot (or by a human) shows the `ci` check running and going green.

## Desired output
Any PR to `main`, opened by anyone (bot or human), gets the same automated quality gate. Broken code can't reach main without a human override.

## Success signals
- Open a no-op PR — CI runs, goes green in <3 min.
- Open a PR with a deliberate type error — CI fails on `typecheck`.
- Open a PR with a deliberate failing test — CI fails on `test`.
- Existing 20 tests all pass against the GH Actions Postgres service container.

## Failure signals
- Tests pass locally but fail in CI (env-var mismatch, migration not run, network reachability to Postgres).
- CI takes >5 min — slows bot iteration; profile and trim if so.
- CI is flaky (intermittent failures unrelated to PR contents) — debug rather than ignore.

## Tests
- Open a deliberate test PR with the workflow file change. Confirm `ci` check appears and runs.
- Open a follow-up test PR with one trivial change. Confirm it goes green end-to-end.
- (Optional) Open a PR that breaks something on purpose to confirm CI catches it; close without merging.

## How to test
1. Branch off main: `git checkout -b hv-032-ci`.
2. Add `.github/workflows/ci.yml`.
3. Push branch, open PR.
4. Watch the Actions tab — the `ci` job should run automatically.
5. If it fails, iterate on the workflow (env vars, service container config, migration step) until green.
6. Squash-merge once green.
7. Open a new throwaway PR (any trivial change) to confirm CI runs on subsequent PRs too.

## Notes
- Postgres service container is the standard pattern for Drizzle/Vitest CI. The user's tests use a real DB (`schema.test.ts`, `access.test.ts`, `projects.test.ts`); we cannot mock-skip this.
- `DATABASE_URL` in CI: `postgresql://postgres:postgres@localhost:5432/bothive_test` (or similar). Must match what `vitest.config.ts` + `drizzle.config.ts` expect.
- Caching `node_modules` via `actions/setup-node@v4`'s `cache: 'npm'` will speed up reruns; worth doing.
- Out of scope: deploying preview environments (intentionally skipped; see FS rationale).
- Out of scope: branch protection rules (HV-033 — separate ticket because it's a github.com settings change, not a repo-file change).

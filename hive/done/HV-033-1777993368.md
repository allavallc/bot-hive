## Goal
Enforce the branch-based workflow at the GitHub level: direct pushes to `main` for source-code changes are rejected; PRs require green CI before merge; bots can self-merge their own PRs once CI passes (so parallelism doesn't bottleneck on human review of every change).

## Why
HV-031 documents the rules and HV-032 installs the safety rail (CI). But docs and CI are advisory until GitHub enforces them. Without branch protection, a bot (or a human in a hurry) can still push directly to main and bypass CI — breaking main, breaking deploy, breaking the whole parallel-bot premise. Branch protection is the *enforcement* layer.

The exception: `hive/`-only commits. Ticket-file moves and hive doc edits are tiny, atomic, and ordered by the git push lock — not source code, no CI value-add. Branch protection should permit these direct-to-main commits while blocking source-code direct pushes. GitHub's "path-based" rules don't exist natively, so the convention is enforced by the rules-file naming (HV-031) and reinforced by code review on substantive PRs.

## Done when

### GitHub settings applied (human action — checklist)

The settings live on github.com under Settings → Branches → "Add rule" for `main`:

- [ ] **Branch name pattern:** `main`
- [ ] **Require a pull request before merging:** ON
  - [ ] **Required approvals:** 0 (bots self-merge — CI is the gate; human acceptance happens at the in-review ticket level, not the PR level)
  - [ ] **Dismiss stale pull request approvals when new commits are pushed:** OFF (no approvals required, so moot)
- [ ] **Require status checks to pass before merging:** ON
  - [ ] Required check: `ci` (the GitHub Actions job from HV-032)
  - [ ] **Require branches to be up to date before merging:** ON (forces rebase before merge — catches stale-branch conflicts)
- [ ] **Require conversation resolution before merging:** OFF (we're not using PR review comments as gates)
- [ ] **Require signed commits:** OFF (out of scope for this ticket; future hardening)
- [ ] **Require linear history:** ON (rebase or squash merges only; no merge commits — keeps history readable for `git log` and provenance scanning)
- [ ] **Allow force pushes:** OFF (would let bots overwrite main; not safe)
- [ ] **Allow deletions:** OFF
- [ ] **Restrict who can push to matching branches:** OFF for now (no admin override needed; revisit if abuse appears)
- [ ] **Do not allow bypassing the above settings:** ON (admins included — no escape hatch for "just this once")

### Auto-merge enabled at repo level

- [ ] Repo Settings → General → "Allow auto-merge" → ON. Lets bots open a PR and click "Enable auto-merge" — when CI goes green, the PR auto-merges. Without this, every PR needs a manual click even when CI is green.
- [ ] Optional: "Automatically delete head branches" → ON. Keeps the repo tidy after merge.

- [ ] `bot-hive/CLAUDE.md` (created in HV-031) gets a new "Branch protection" section explaining what's enforced and why. Bots reading it understand they cannot push to main for source code — the push will be rejected by GitHub regardless of local intent.
- [ ] `hive/HIVE.md` "Working in parallel" section (added in HV-031) gets a one-paragraph note that branch protection is the enforcement mechanism — format-neutral wording so other adopters know to set up the equivalent on their own host (GitHub, GitLab, Bitbucket, etc.).

### Verified end-to-end

- [ ] Open a throwaway PR. Confirm the `ci` check is **required** (PR shows "Required" badge next to the check).
- [ ] Try `git push origin main` directly with a source-code change. Confirm it's **rejected** with branch-protection error.
- [ ] Try `git push origin main` with a `hive/` ticket-file change. Confirm it **succeeds** (path-based isn't enforced by GitHub natively, but the convention holds because hive moves are small atomic commits — the rule is documented in HV-031, the enforcement is honor-system within `hive/`).
  - **Caveat:** GitHub branch protection is all-or-nothing on a branch — there's no native "allow these paths, block those." So technically, branch protection blocks ALL direct pushes to main, including `hive/`. We have two options:
    - **A. Accept the friction:** even hive/ moves go via PR + auto-merge. CI runs on every hive/ move (wasteful but harmless — typecheck/lint/test will all pass since no source changed).
    - **B. Skip protection entirely** and rely purely on the documented rule + PR review pressure. Less safe.
  - **Recommendation: A.** Auto-merge makes the friction near-zero (bot opens PR, CI passes in <1min, auto-merges). The wasted CI cycles are cheap. This means HV-031's "hive/ is main-direct" rule changes to "hive/ is PR-with-auto-merge."
- [ ] Open a PR with a deliberate test failure. Confirm CI fails and the PR is **blocked** from merging until fixed.
- [ ] Open a clean PR. Confirm CI passes and auto-merge fires.

## Desired output
GitHub enforces what the docs say. Bots can't accidentally (or intentionally) bypass CI. Direct-to-main pushes for source code are rejected. Auto-merge means bots ship without humans in the loop on every PR — CI is the gate.

## Success signals
- A bot tries to push source directly to main → push rejected → bot follows the documented PR path.
- A bot opens a PR with broken code → CI fails → merge blocked → bot iterates.
- A bot opens a PR with green code → auto-merge fires → main updates → deploy.
- Two bots open PRs simultaneously → both auto-merge in sequence (second one rebases first via "branch up to date" requirement) → no manual intervention.

## Failure signals
- Branch protection set up wrong → bots can still push to main → premise of the FS broken.
- Auto-merge not enabled → every PR sits open waiting for click → parallelism collapses on human bottleneck.
- "Require branches up to date" off → bots merge stale branches → main gets surprises that didn't run on CI.

## Goal
Configure Better Auth's GitHub provider to request the `repo` scope so the app can list a signed-in user's accessible repos (public + private) via their OAuth token.

## Why
FST-003 derives project access from GitHub repo collaborator status. Reading the user's repo list requires `repo` scope — `public_repo` alone leaves any private-repo collaborator locked out.

## Done when
- `src/lib/auth.ts` GitHub provider config requests `repo` scope.
- Sign-in completes; `account.scope` row in DB shows `repo`.
- `octokit.repos.listForAuthenticatedUser({ visibility: 'all' })` returns private repos for an account that has them.

## Desired output
After signing in, the stored OAuth token can read every repo the user has access to on GitHub.

## Success signals
- DB: `account.scope` includes `repo`.
- Manual call to `listForAuthenticatedUser` returns private repos.

## Failure signals
- 403 / `insufficient_scope` on Octokit calls — usually means stored token predates the scope change; user re-auths to fix.

## Tests
- Manual: sign out, sign in, inspect `account.scope`. Automated coverage is impractical for OAuth flows; HV-018 covers downstream behaviour.

## Notes
- `repo` is GitHub's broad scope. Fine-grained PATs / GitHub-App user-to-server tokens are narrower but don't integrate with Better Auth today. Defer.
- No backfill needed — no real users yet.

## Goal
Add a convention to AGENTS.md and HIVE.md: before an agent claims any new ticket via DAG-walk, it must first scan `hive/in-progress/` for tickets where `Assigned to:` matches its handle AND `Rejected by:` is populated. Those are the agent's own pending rework — they ship first. Only after no such tickets exist does the agent proceed to claim new work.

## Why
CC2 raised this gap during the first end-to-end rejection test (2026-05-06). Today's flow:

1. Bot A claims HV-X, builds it, moves to in-review.
2. Human rejects HV-X — ticket moves back to in-progress with `Rejected by`, `Rejection reason` populated. Still assigned to Bot A.
3. Bot A's next session start runs DAG-walk for new claims. Sees HV-X in `in-progress/` and **skips it** (in-progress = "claimed, not available"). Bot A picks something else.
4. HV-X sits as a half-finished, rejected ticket. Either Bot A never returns to it, or it eventually triggers HV-050's stale-claim reclaim and gets picked up by another agent — context-loss every time.

The convention should encode that **rejection is an iteration signal, not an abandonment signal.** The original agent (or whichever agent is online next under that handle) is the right party to fix it, because they have the freshest mental model of what they shipped. New agents picking up rejected work pay a context-switch tax that Bot A wouldn't.

## Done when

### Convention installed in AGENTS.md and HIVE.md

In the "Picking what to claim" section, **before** the DAG-walk steps, add a new pre-step:

> **0. Pre-claim ritual: pick up your own rejected work first.**
>
> Scan `hive/in-progress/*.md`. For each ticket where the `Assigned to:` field's handle equals **your** session handle AND the `Rejected by:` field is populated:
>
> - This is your pending rework. Read the `Rejection reason:` carefully — that's the spec for the next iteration.
> - Resume work on it. Append to `events.log`: `<ISO> <hv-id> reclaimed-after-rejection <handle>`.
> - Skip the rest of the DAG-walk. Don't claim a new ticket while you have rejected work outstanding.
>
> If no such tickets exist, proceed to step 1 (DAG-walk).

### Add to the session-start checklist

The existing 5-step session-start checklist gets a 6th step (or insert as 5b):

> 6. Scan `hive/in-progress/` for tickets assigned to you with `Rejected by:` populated. Those are your pending rework — handle them before claiming new work.

### Edge case documentation

Document the interaction with HV-050 (stale-claim watchdog):
- If a rejected ticket assigned to a different handle is stale (>2h since `Last touched:`), the standard reclaim rule applies — any agent can reclaim it.
- If a rejected ticket is yours AND fresh (active session), it's your responsibility, not the swarm's.

## Desired output
A bot that built HV-X, had it rejected, and starts a fresh session sees HV-X waiting in `in-progress/` with the rejection reason and immediately resumes work on it. No other bot has to context-switch in. Rejection becomes a tight loop instead of a slow handoff.

## Success signals
- A rejected ticket assigned to an active agent is back in-progress (with new commits) within the agent's next action cycle.
- No rejected ticket sits idle for >2h before either the original agent picks it up or HV-050's stale-reclaim fires.
- The "rejected → context-loss → re-litigate" pattern from today's session doesn't recur.

## Failure signals
- Agents skip the pre-claim ritual and the rejected ticket sits anyway. Mitigation: the convention is enforced socially + by code review of session behavior; could later become runtime-enforced if it's an issue.
- Agents loop on rejected work indefinitely (e.g., rejection reason is unclear → keep failing → keep claiming). Mitigation: after 2 rejection cycles, escalate to `hive/questions-for-human.md` rather than try a third time.

## Tests
- Manual: human rejects an in-review ticket. Same agent (or a fresh session under the same handle, e.g., via `BOT_HIVE_HANDLE` override) starts a new turn. Confirm it picks up the rejected ticket before any DAG-walk claim.
- Manual: human rejects a ticket. The original agent's session ends. After 2h, HV-050's stale-reclaim makes the ticket available to any agent. Confirm a different agent can pick it up after the timeout.

## How to test

## Notes
- Filed during today's first parallel-bot rejection test. CC2 noticed that there's nothing in the protocol that routes a rejected ticket back to its original handler — DAG-walk just sees it as in-progress and skips it.
- This complements HV-050 (stale-PR watchdog) and HV-046 (human-friendly rejection flow). Together: rejection is a structured loop with priority routing + handle-based ownership + stale-claim safety net.
- Out of scope: reassignment when the original agent is unavailable for a long time. HV-050's 2-hour stale-claim threshold is the safety net.
- Out of scope: forcing the original agent to address rejected work — agents are still autonomous; if they refuse, the stale-claim path catches it eventually.
- Two rejection cycles is a soft limit; codifying that as "after N rejections, escalate" can be a follow-up if it becomes an issue.

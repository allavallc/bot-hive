## Goal
Add a convention to AGENTS.md and HIVE.md: when an agent's work adds a new infrastructure requirement (env var, GitHub App permission, secret, package, port, OAuth scope), the same agent also ships the corresponding doc update for the operator runbook (`docs/DEPLOY.md`) and any related setup docs. The author of the dependency owns the doc update — no exceptions, no "we'll do it later."

## Why
Caught live during today's session — CC2's HV-046 (accept/reject flow) introduced a new GitHub App permission requirement (`Pull requests: Read & write`) to call the PR-create API. The runbook (`docs/DEPLOY.md`) wasn't updated, so the operator (the user) hit a "failed to create PR" error with no breadcrumb pointing at the missing permission. ~20 min of debugging that a 30-second doc edit at PR-time would have prevented entirely.

This isn't a one-off. The pattern recurs:
- A feature that needs a new env var → docs/DEPLOY.md's env-var checklist goes stale
- A migration that needs a new Postgres extension → setup notes don't mention it
- A code path that calls a new external API → secrets list doesn't reflect the new scope
- A package upgrade that requires a Node version bump → README's prerequisites lie

The cost compounds: each undocumented dependency is a paper cut for the next operator. After 10 of them, "the docs are useless" is the truth.

The fix is a convention, not infrastructure: if you add a dependency, you own the doc update. Same PR if possible; immediate follow-up PR if not.

## Done when

### Convention installed in AGENTS.md and HIVE.md

In the "Working in parallel" section, add a new subsection (after "Stale-PR watchdog" or in a similar location):

> **Owning doc updates when you add an infra dependency**
>
> When your work adds a new infrastructure requirement — env var, GitHub App permission, secret, package, port, OAuth scope, anything an operator needs to set up — you also own the corresponding doc update.
>
> Concretely:
> - New env var → update `.env.example`, `render.yaml`, and `docs/DEPLOY.md`'s env-var checklist.
> - New GitHub App permission → update `docs/DEPLOY.md` Step 2 to include the permission, and note that adding a permission to an existing App requires re-approving the install.
> - New required package or version bump → update `README.md` prerequisites.
> - New external API or scope → update the secrets list in `docs/DEPLOY.md`.
>
> The fix lands in the **same PR** as the code change when feasible. If the doc update is large enough to warrant its own PR (rare), the author files an immediate follow-up ticket assigned to themselves and ships it within the same session.
>
> **Doc drift is real cost.** The next operator hitting an undocumented dependency pays minutes-to-hours of debugging that the original author could have prevented with a 30-second edit. The convention exists to make that explicit and uncomfortable to skip.

## Desired output
The next time an agent adds a new env var or permission, the corresponding doc update lands in the same PR — or as an immediate follow-up that the author owns. No more "operator hits an undocumented dependency" surprises.

## Success signals
- Within the next 5 PRs that add an infra dependency, the doc update is also present (or immediately filed).
- The "doc drift" failure mode (today's HV-046 GitHub App permission) doesn't recur.
- Code reviewers (humans or other agents) flag missing doc updates as a routine review comment.

## Failure signals
- Agents skip the convention and ship a feature without the doc update, then "forget" to file the follow-up. Mitigation: code review should catch this; if it doesn't, escalate the rule to a CI check (e.g., a script that flags PRs touching `.env.example` without a corresponding `docs/DEPLOY.md` change). That escalation is its own future ticket if needed.

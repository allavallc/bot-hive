## Goal
Define the Drizzle schema for every Phase-1 table and produce the first migration.

## Why
Defining the full schema up front prevents reshuffling foreign keys mid-build.

## Done when
- `src/db/schema.ts` defines Better Auth tables (`user`, `session`, `account`, `verification`) and Hive tables (`projects`, `tickets`, `features`, `webhook_deliveries`, `sync_state`).
- `src/db/index.ts` exports a typed Drizzle client bound to `DATABASE_URL`.
- Unique constraints: `(project_id, hv_id)` on tickets, `(project_id, fs_id)` on features, `(owner_id, github_repo, install_id)` on projects.
- `webhook_deliveries` PK is composite `(project_id, delivery_id)` (same delivery may be processed for multiple projects sharing a repo); `sync_state.project_id` is PK.
- All FKs to `projects` are `ON DELETE CASCADE`. `users → projects`, `users → sessions`, `users → accounts` cascade.
- `drizzle-kit generate` produces a migration that `npm run db:migrate` applies cleanly to a fresh DB.

## Desired output
Later tickets `import { db, tickets } from "@/db"` and get fully-typed queries.

## Success signals
- `npm run db:migrate` is idempotent.
- All Phase-1 queries compile against the generated types without `as any`.

## Failure signals
- Hand-edited migrations diverge from `schema.ts`.
- Cascade behavior wrong: deleting a project leaves orphan tickets.

## Tests
- Manual: drop DB, migrate, `\d` every table.
- Unit: duplicate `(project_id, hv_id)` insert fails.
- Unit: duplicate `delivery_id` insert fails.

## Notes
- `tickets.frontmatter` is `jsonb` so new fields don't require migrations.
- App-table IDs are UUIDs (`uuid` + `defaultRandom`); Better Auth tables use `text` IDs per Better Auth's canonical Postgres schema.
- `tickets.state` is `text` (not enum); adding bot-horde states needs no migration; validation is Zod-side.
- `install_id` is `bigint` — GitHub installation IDs can exceed int4.
- `updated_at` uses Drizzle `$onUpdate`; no Postgres trigger (revisit if non-Drizzle writers appear).
- Multi-user-same-repo (Model A): each user owns their own `projects` row; webhook handler fans out across all matching rows.
- Vitest is not yet installed; the two unit tests in this ticket's Tests section run after Vitest setup lands. Manual `\d` verification + idempotent re-migrate is the Phase-1 acceptance.
- Webhook-deliveries prune job is a separate later ticket.

## Resolution
- Migration: `drizzle/0000_same_sabra.sql` — 9 tables, 7 FKs (all cascade), 3 indexes, 3 uniques, 2 composite PKs.
- Verified: `npm run db:migrate` is idempotent (re-run is no-op via `__drizzle_migrations` tracking). `\d` confirms cascades and constraints on `projects`, `tickets`, `webhook_deliveries`. Typecheck + lint clean.

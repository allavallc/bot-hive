## Goal
Enable GitHub's merge queue on main so source-code PRs land in batches instead of one-at-a-time-with-fresh-CI-each. HV-079 (paths-aware CI) handles coordination-metadata PRs by skipping CI; HV-080 handles the harder case of source PRs by batching them so multiple PRs share a single CI cycle.

## Why
With auto-merge + serial landings + per-PR full CI, N pending source PRs cost N × ~3 min wall time (and N × CI minutes). The last PR to merge waits for every earlier one's CI cycle. As Bot Hive's swarm grows, this becomes the dominant friction even after HV-079.

GitHub's merge queue is the canonical fix:
- The queue accepts PRs as they're approved + auto-mergeable.
- It builds a "batch" branch that combines several PRs at once, runs CI on the batch, and merges the batch atomically when CI passes.
- N PRs → 1 CI cycle (or a small number of batches), not N CI cycles.

## Done when

### Branch protection rule
- "Require merge queue" enabled on `main` via the GitHub Settings → Branches → main rule (or via `gh api` automation).
- Queue config: max group size 5, min group size 1, max wait time 5 minutes, merge method squash (matches today).
- "Require pull request reviews before merging" stays disabled (auto-merge-only model).
- "Require status checks to pass before merging" requires `ci` (unchanged).

### CI workflow
- `.github/workflows/ci.yml` adds `merge_group:` to its `on:` trigger so CI runs on the merge-queue's batch commits.
- The `detect` job (HV-079) handles `merge_group` events the same way as `pull_request` — checks the merge-queue commit's diff against main.

### Verification
- After enabling, open 3+ source PRs simultaneously, all auto-mergeable. Confirm GitHub batches them into a single merge-queue group, runs CI once, merges atomically.
- Hive-only PRs continue to land instantly via HV-079.
- Document the new flow in `docs/DEPLOY.md` (operator runbook) and AGENTS.md (so agents know auto-merge-via-queue is the new default).

## Out of scope
- Custom batch-grouping logic (e.g., "always batch FS-007 PRs together"). The default GitHub queue heuristics are fine for v1.
- Rollback strategy if a batch fails CI. GitHub's queue handles this — bisects to find the bad PR, kicks it out, retries the rest. No additional logic needed.

## Goal
A bot running locally can authenticate to the Bot Hive HTTP API using a project-scoped Bearer token, separate from the human's web-app session. The token is created (POST), revoked (DELETE), and validated by the same code path that today only accepts session cookies. This unblocks bots publishing on the SSE signal channel — currently file-based via `presence.log` because bots have no HTTP auth.

## Why
The signal channel (HV-047) is half-shipped: humans can publish via the swarm panel (which uses the session cookie), but bots can't. As a workaround, presence (HV-061) lives in `presence.log`. Once bot tokens exist, presence + claim/done/blocked/note signals can all flow on the SSE channel directly, sub-second, with the swarm panel as the live view.

This is also the prerequisite for several future improvements:
- Hard-lock signals on the SSE channel (HV-063 follow-up).
- Bot-side metrics / heartbeat publishing.
- Per-bot rate limiting (the API can attribute requests to a specific token).

## Done when

### Database
- New `bot_tokens` table:
  - `id` uuid pk
  - `project_id` text fk → `projects.id` (cascade delete)
  - `created_by` text fk → `user.id` (the user who issued it)
  - `display_name` text not null (e.g., "kestrel laptop", "ci-runner")
  - `token_hash` text not null (sha256 of the raw token; raw is shown once on creation, never stored)
  - `last_used_at` timestamp nullable
  - `revoked_at` timestamp nullable
  - `created_at` timestamp default now()
  - Index on `(project_id, revoked_at)` for fast lookup of active tokens per project
- Migration generated via `drizzle-kit generate` and committed.

### Token generation + hashing
- `src/lib/bot-tokens.ts`:
  - `generateToken()` returns a base64url-encoded 32-byte random token, prefixed with `bh_` so it's identifiable as a Bot Hive token in logs / leaks.
  - `hashToken(raw)` returns `sha256(raw)` hex (sha256 is fine — these are random tokens, not user passwords).
  - `createToken({projectId, createdBy, displayName})` inserts a row, returns `{tokenId, raw}`. Raw is shown to the caller once; only the hash is stored.
  - `validateToken(raw)` looks up `token_hash`, checks `revoked_at is null`, updates `last_used_at`, returns `{tokenId, projectId, createdBy, displayName}` or null.
  - `listTokens(projectId)` returns name + lastUsed + createdAt + isRevoked (no raw, no hash).
  - `revokeToken(tokenId)` sets `revoked_at = now()`.

### Actor helper
- `src/lib/actor.ts`:
  - `getActor(req, projectId)` returns one of:
    - `{kind: "user", userId, displayName}` — when a Better Auth session cookie is present and valid for the project.
    - `{kind: "bot", tokenId, projectId, displayName}` — when `Authorization: Bearer bh_<token>` is present, valid, not revoked, and scoped to the requested `projectId`.
    - `null` — neither auth method works.
  - Existing routes that today call `auth.api.getSession` and `getProjectForUser` migrate to call `getActor` instead.

### Endpoints
- `POST /api/projects/[id]/bot-tokens`:
  - Auth: session cookie only (humans create tokens; bots can't bootstrap themselves).
  - Body: `{displayName: string}` (1–64 chars).
  - Response: `{tokenId, raw, displayName, createdAt}` — raw is shown once and never returned again.
- `GET /api/projects/[id]/bot-tokens`:
  - Auth: session cookie.
  - Returns: list of tokens for the project (no raw, no hash; just metadata).
- `DELETE /api/projects/[id]/bot-tokens/[tokenId]`:
  - Auth: session cookie.
  - Sets `revoked_at = now()`.
- Update `POST /api/projects/[id]/signals` to call `getActor` — accepts both auth methods. When called with a bot token, the published signal has `bot: <displayName>` populated.
- Update `GET /api/projects/[id]/signals/stream` to call `getActor` — same.

### CLI helper
- `scripts/create-bot-token.sh` (and `.ps1`):
  - Takes `--project <id> --name <displayName> --cookie <session-cookie>` args.
  - POSTs to the create endpoint; prints the raw token + the curl command to use it.
  - Documented in `docs/BOT_TOKENS.md` (new file in `docs/`).

### Tests
- `src/lib/bot-tokens.test.ts`:
  - `generateToken` produces unique 32-byte base64url with `bh_` prefix.
  - `hashToken` is deterministic.
  - `createToken` + `validateToken` roundtrip on a real token.
  - Revoked token fails validation.
  - Token for a different project fails validation when `getActor` is called with a project mismatch.
- `src/lib/actor.test.ts`:
  - Session-only request → `{kind: "user", ...}`.
  - Bearer-only request with valid token → `{kind: "bot", ...}`.
  - Bearer with revoked token → null.
  - Bearer with token for a different project → null.
  - Both auths present → session wins (predictable).
- Both test files use the existing `test-db.ts` per-test rollback fixture.

## Notes
- sha256 is fine for token storage because the raw token is 32 random bytes — no rainbow-table risk. bcrypt would be unnecessary CPU cost on every signal POST.
- The `bh_` prefix lets us grep logs for accidentally-leaked tokens (e.g., a careless echo in a script).
- Once this lands, `presence.log` can either stay (durable presence over git) or migrate to SSE; that's a HV-061 follow-up decision.

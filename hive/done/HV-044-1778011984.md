## Goal
Each feature set keeps an evolving "Architecture & decisions" section inside its `feature-set-NNN-<slug>.md` doc. Bots and humans append entries as design choices are made. Future agents working in that FS read the section before starting and avoid re-litigating settled questions. Decisions accumulate; the FS doc becomes the swarm's institutional memory for that scope.

## Why
Today's coordination artifacts capture **what happened** (events.log, ticket files, git log) but not **why we chose this shape**. Two failure modes follow:

1. **Re-litigation.** A new bot working in an existing FS hits a question that was already answered, doesn't know there's history, and chooses differently — or burns time deciding from scratch.
2. **Design incoherence.** Bot A introduces helper `parseAssignee()`; Bot B independently introduces `extractHandle()` for the same purpose. Both ship. Code is now incoherent at the conceptual layer even though no source files literally collided. The current swarm protocol prevents file-level collisions but not design-level ones.

The fix is durable: a written record of *the decisions* — choice, rejected alternatives, rationale, implications, ticket reference — co-located with the FS that owns them.

## Done when

### Convention installed

- Each `hive/feature-sets/feature-set-NNN-<slug>.md` has a new section `## Architecture & decisions` after `## Status`. Format per entry (compact ADR-style):

  ```markdown
  ### YYYY-MM-DD — <one-line headline> (<bot-handle>)

  **Choice:** <what we picked>

  **Rejected:** <what we considered and why we didn't pick it>

  **Why:** <substrate-portable rationale; not implementation detail>

  **Implications:** <what now changes in the code or convention>

  **Reference:** <HV-XXX / PR #N>
  ```

- Bots append a decision entry whenever they make a non-trivial design choice that future bots in the same FS might revisit. "Non-trivial" = anything you'd debate in a code review with a senior engineer; pure mechanical edits don't qualify.
- Bots **read the relevant FS's decision section on session start** (after `focus.md` and `events.log`). If `focus.md` names an FS, the FS's decisions are mandatory pre-reading.
- The append-on-decision rule is documented in **`AGENTS.md`** ("Working in parallel — the swarm protocol" section) and **`hive/HIVE.md`** ("Working in parallel" section). One paragraph each.

## Desired output
A bot opening FS-007 (or any FS) on a future date reads the Architecture & decisions section first, sees "we chose transactional rollback over Date.now() patches; rejected the patch path explicitly; here's why," and doesn't waste cycles re-deciding. Design coherence emerges from shared institutional memory.

## Success signals
- A new bot session, told to work on tickets in an existing FS, references prior decisions in its own commits/comments.
- Code reviews catch fewer "wait, didn't we already decide X" moments.
- The FS docs themselves become the durable artifact future readers look at first — more than git log, more than the event log.

## Failure signals
- Bots forget to append decision entries — the section grows stale or empty for active FSes. Mitigation: convention is enforced socially and by code review.
- Decisions grow into chapters instead of compact entries. Mitigation: hard length budget per entry (~10 lines max). If a decision needs more, it deserves its own design doc and a single entry pointing at that doc.
- The section bloats past usability. Mitigation: split into `feature-set-NNN-decisions.md` only if the parent FS doc exceeds ~500 lines. Default stays inline.

## Tests
- Manual: a fresh bot session asked "what's the architecture of FS-007?" should be able to answer from the doc alone, without re-reading the codebase.
- Manual: two bots simultaneously appending to the same FS's decision section produces two ordered entries (no merge conflict beyond what auto-rebase handles).

## Notes
- **Why per-FS, not project-wide.** Decisions scoped to one FS shouldn't pollute a global ADR log. FS-007's transactional-rollback decision is FS-007 context; FS-010's modal-card decision is FS-010 context. Co-location keeps the right context together. A future cross-cutting `ARCHITECTURE.md` (or section in `AGENTS.md`) can hold project-wide calls — out of scope here.
- **Why inside the FS doc, not a separate file.** One file per FS keeps the institutional memory together. Split only if the doc exceeds ~500 lines (heuristic, not rule).
- **Format choice.** Compact ADR-style. Industry-standard pattern, scales to many decisions, optimized for quick reading rather than exhaustive coverage. We're not writing RFC 9293; we're leaving notes for the next bot.
- **Why High priority.** Every FS we ship without this section loses institutional memory. Cheap to add now, expensive to backfill later. FS-008, FS-009, FS-010 are all in flight; getting the convention installed before they accumulate decisions saves real archaeology cost down the road.
- Out of scope: project-wide ARCHITECTURE.md (later, if needed); migrating decisions out of git commit messages into this format (only forward-going decisions get captured systematically).
- This was identified as a gap during the parallel-bot session on 2026-05-05. The user explicitly approved: per-FS only, inside the FS doc, retroactive FS-007 population is "important but not urgent," priority High.

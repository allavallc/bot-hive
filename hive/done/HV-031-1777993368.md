## Goal
Establish, in writing, the swarm coordination protocol every bot and human follows when working in this repo — and in any repo using the hive format. Source-code work goes on a feature branch and lands via PR + CI. Only `hive/` coordination metadata commits direct to main. Bots read a shared focus signal, walk the dependency DAG with a cohesion preference, leave stigmergic timestamps, publish to an event log, and escalate any real conflict to humans rather than guessing.

## Why
Bot Hive's existing workflow is unsafe under parallelism — two bots editing the same source on main corrupts commits. The naive fix ("branch and PR") solves source-file collisions but doesn't address the deeper coordination problem: how do multiple autonomous bots divide work, hand off, and recover from each other's failures without a central controller?

The answer is in nature and in robotics: swarms don't have coordinators. Boids align, cohere, and avoid each other using local rules and a shared environment. ROS robots use pub/sub topics with no point-to-point messaging. Bot Hive should do the same — and conveniently, **git is already a pub/sub system** (commit = publish, pull = subscribe, directory tree = topic structure). We just need a few conventions on top to make the swarm behavior emerge.

This ticket installs those conventions across `bot-hive/CLAUDE.md` (project), `hive/HIVE.md` (format spec, applies to anyone using hive on any repo), and `README.md` (entry-point pointer). It also defines the conflict-response policy so bots self-recover from trivial git mechanics but escalate substantive conflicts.

## Done when

### Conventions installed

The following conventions are documented in both `bot-hive/CLAUDE.md` (project-specific) and `hive/HIVE.md` (format-neutral). Any bot reading either file knows the protocol.

1. **`hive/focus.md`** — alignment signal. A one-line file the human edits with the current standing order. Format: `current = feature-set-007` or `current = HV-031` or `current = backlog`. Bots read this on every session start and treat it as their working scope. The chat-channel "do FS-X" instruction always also updates this file — it is the source of truth, not the chat message.
2. **DAG-walk with cohesion preference** — work selection. On session start, after pulling: (a) read `focus.md`, (b) collect every ticket in scope with no unfinished blockers and not in `in-progress/`, (c) pick the leaf that unblocks the most downstream tickets (cohesion preference — bots converge on the critical path). Tie-break: lowest ticket ID. This rule is deterministic enough that two bots running it at the same moment usually pick different leaves; if they pick the same, the git push lock breaks the tie and the loser re-runs.
3. **`**Last touched:**` ticket field** — stigmergic timestamp. Every commit a bot makes against an in-progress ticket also updates this field. If `Last touched:` is older than **2 hours**, any other bot may reclaim the ticket (move back to backlog with a `**Reclaim reason:**` note, or take it over). Bots refresh on every commit; healthy bots never go stale.
4. **`hive/events.log`** — append-only event topic. Bots publish one-line events here on lifecycle transitions: `2026-05-05 10:30 HV-019 done — HV-020 unblocked` or `2026-05-05 10:45 HV-031 in-review`. Bots tail the log on session start to catch up on what changed. The log is durable history; the file format is one event per line, ISO timestamp, ticket ID, action, optional unblocked-list.
5. **`hive/questions-for-human.md`** — async escalation channel. When a bot needs a human decision (ambiguity, scope question, conflict it can't resolve), it appends to this file rather than blocking on chat. Human reads on their cadence, answers in chat or by editing the file. Keeps bot work flowing without spamming.

### Workflow rules installed

6. **Source code goes on branches.** Any commit that touches `src/`, `tests/`, `migrations/`, configs, or any file outside `hive/` MUST go on a feature branch named `hv-XXX-<slug>` and land via PR. Direct pushes to main for source-code work are forbidden (and will be enforced by branch protection in HV-033).
7. **`hive/` work is main-direct.** Ticket-file moves, hive doc edits, feature-set docs, and the conventions files (`focus.md`, `events.log`, `questions-for-human.md`) commit straight to main. The git push lock orders concurrent moves — losers retry.
8. **Always `git pull` before claiming or committing to main.** Stale local main = guaranteed push conflict. The pull is the subscribe step.

### Conflict-response policy installed

| Failure case | Bot behavior |
|---|---|
| Push fails on `hive/` ticket move (someone else pushed first) | `git pull --rebase` and retry. Standard. |
| `git rebase main` on PR branch produces no conflict markers | Push --force-with-lease, let CI re-run. |
| `git rebase main` produces real conflict markers | **Stop. Never guess.** Move ticket to `hive/blocked/`, set `Failure mode: merge-conflict`, comment the PR explaining what's blocking, append to `hive/events.log`. Human resolves. |
| CI fails on PR | Read CI output, attempt fix, push fix, wait for CI. Two attempts max. If still failing, move to `hive/blocked/` with `Failure mode: failed-tests`. |
| Stale claim discovered (Last touched > 2h) | May reclaim by moving back to backlog with `**Reclaim reason:**` set, or take over by reassigning. Append to `events.log`. |

The hard rule: **bots auto-resolve trivial git mechanics (rebases that come clean, push retries, CI fixes within two attempts) but escalate any substantive conflict.** Bots NEVER attempt to merge or guess code resolution.

### Substrate-vs-conventions disclaimer included

Both `CLAUDE.md` and `HIVE.md` include a short note explaining: the **conventions** (focus signal, DAG walk, stigmergic timestamps, events log, no central authority, failure-tolerance) are the long-term design. The **substrate** (git as the broker, file system as topics, pull-based polling) is appropriate for current scale (~2-20 agents). At higher scale, the substrate evolves (Redis/Postgres for events and locks) but the conventions stay the same. This frames future readers correctly: don't redesign conventions when scaling, swap substrates.

## Desired output
A bot entering this repo for the first time reads `CLAUDE.md` or `HIVE.md` and immediately knows: read focus, walk the DAG, claim a leaf, branch for source, push hive/ to main, escalate real conflicts. Two bots converge naturally on different work because the rules are deterministic. The user keeps a hand on intent (focus.md) and on acceptance (in-review), but doesn't have to choreograph the bots.

## Success signals
- Two Claude sessions on different computers can work on the same FS without colliding.
- A bot that finishes a ticket sees its handoff (the unblocked downstream) without needing the human to relay.
- A bot that hits a real merge conflict surfaces it cleanly (ticket → blocked, PR comment, events.log entry) — no silent guess-merging.
- A fresh reader (human or bot) reading just `CLAUDE.md` understands the workflow well enough to participate.
- The same conventions hold up if the substrate is later swapped (Redis events.log, Postgres claim table) — the bot logic doesn't have to change.

## Failure signals
- A bot reads CLAUDE.md and still tries to commit source-code changes directly to main.
- The conflict-response table is buried so deep nobody finds it.
- HIVE.md and CLAUDE.md disagree on a detail — confusing to bots.
- Bots fight over the same leaf instead of converging on different work (DAG walk isn't deterministic enough).
- A bot dies and its claim sits in in-progress for days (stigmergic timestamp not enforced).

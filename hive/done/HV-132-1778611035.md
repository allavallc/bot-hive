## Goal

Expose the seat map on the read side (one endpoint) and render it on the kanban so the operator can scan colony state at a glance and watch shifts happen live.

## Concrete changes

- **`src/app/api/bots/colony/route.ts`** — new GET handler. Query param: `repo_full_name`. Resolves `projects.id`. Returns all active rows grouped by colony, seat-ascending: `{ colonies: [{ colony, seats: [{ handle, seat, role, joined_at, last_heartbeat_at }, ...] }, ...] }`. Calls `sweepStale` first so the response reflects current liveness. `export const dynamic = "force-dynamic"`.
- **`src/app/projects/[id]/seat-strip.client.tsx`** — new client component. On mount, fetches `/api/bots/colony` for the current project's repo. Subscribes to the existing SSE stream at `/api/projects/[id]/stream` (the same pattern as `src/app/projects/[id]/board.client.tsx`) and updates local state on `bot-left` and `bot-joined` events: replace the affected colony's seat list with `event.seatMap`.
- **Board integration** — mount `<SeatStrip projectId={...} githubRepo={...} />` on the project page. **Placement must be approved before build** per HIVE.md's UI-approval rule (see Notes).
- **Tests** — `src/app/api/bots/colony/route.test.ts` (empty colony, active rows, stale rows swept on request). Component test for `seat-strip.client.tsx` if a snapshot is cheap; otherwise manual smoke covered in Done-when.

## Notes

**Layout proposal needed before build.** Per `hive/HIVE.md` ("UI changes need explicit visual approval before build"), the developer claiming this ticket must post a placement proposal in `hive/notes-to-humans/<bot>.log` and wait for explicit "go" from the operator before writing UI code. Two plausible homes: (a) top of the board, full-width strip above the column headers; (b) inside the existing swarm-panel client component (`src/app/projects/[id]/swarm-panel.client.tsx`) as a new subsection. The ticket does not pre-decide.

**Why `/colony` is its own endpoint, not bundled into `/whoami`.** `/whoami` returns one bot's view; `/colony` returns the whole map for the project. The UI needs the latter; bots only need the former. Keeping them separate avoids over-fetching from the script path.

**Existing SSE infra is reused.** `src/lib/broadcast.ts` already broadcasts per `projectId`; the kanban's SSE route at `src/app/api/projects/[id]/stream/route.ts` already calls `subscribe(projectId, fn)`. Adding `bot-left` / `bot-joined` events (done in HV-131) means the strip just adds a discriminator to its existing SSE handler.

**Out of scope:**
- Per-bot detail drawer (clicking a seat chip) — file as follow-up if useful.
- Seat history / who-held-which-seat over time — historical view is a different feature (FS-004 territory).

**Risk.** The strip groups by colony. A project today is typically single-colony (one operator's bots), but the schema allows multiple colonies per project. If the strip becomes cluttered with multiple colonies, scope a follow-up to add a colony filter.

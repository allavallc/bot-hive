## Goal
Three protocol gaps surfaced during the first 3-bot stress test. Fixes them in one bundled docs update so the swarm protocol catches up to the architecture (per-actor event logs, cleared zombie tickets, third active bot).

## The three fixes

### 1. Pull-before-claim, not just session-start
Sparrow claimed HV-081 from a stale local clone (PR #132 had retired the ticket to `not-doing/` 30 minutes earlier). Sparrow followed the protocol correctly — its session-start `git pull` happened before #132 merged. The protocol gap: there was no rule requiring a fresh pull before each claim.

**Rule installed**: every DAG-walk runs `git pull --rebase` immediately before scanning AND immediately before the `git mv` claim. Cost is one round-trip; benefit is eliminating the "worked on a retired ticket" failure mode.

### 2. Handle-collision lock via the per-actor file itself
Two bots both auto-picked `falcon` because the collision-check is best-effort and TOCTOU-racey when bots start within seconds of each other. Neither saw the other's commit yet because neither had committed.

**Rule installed**: handles are picked from `hive/handles.txt` (a new pool file in the repo). Bot picks the first handle without an existing `hive/events/<handle>.log` file, then **immediately commits a `presence` line** to that file. If the push fails (non-fast-forward), the loser detects the collision via the rebase, rolls back, picks a different handle. The git push race IS the lock — no separate registry, no heartbeat, no liveness logic.

**Sub-decision**: handles are session-unique and **never reclaimed**. A bot's events log stays as audit history; new sessions get fresh handles. Avoids the ambiguity of "is the original `falcon` still alive or did `falcon` get reused?" Continuity across restarts is via `BOT_HIVE_HANDLE` env override.

### 3. Feature-set status — `active` / `future` / `done`
A new ticket filed under a "future" FS lands in `backlog/` and is immediately pickable. The human ends up retiring each ticket the swarm tries to claim. The fix is one signal at the FS level.

**Rule installed**: each FS file has a `**Status**: <active|future|done>` line in its header. DAG-walk reads each candidate ticket's `Feature set:` field, opens the FS file, skips the ticket if `Status:` is not `active`. To park a whole FS: edit the FS file, set `Status: future`, push. Bots skip its tickets on next pull.

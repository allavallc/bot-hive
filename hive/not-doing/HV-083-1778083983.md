## Note — why this is not-doing
HV-087 split `hive/events.log` into per-actor `hive/events/<actor>.log` files. Each per-actor file is naturally chronological (one writer, append-only). The merged view is sorted at *read time* by the `/api/projects/[id]/events` endpoint — no on-disk sort needed. The legacy `events.log` is frozen; the merge=union driver that this ticket was supposed to backstop is no longer the contention point.

## Goal
A cron that runs every 30 min, reads `hive/events.log`, sorts entries by ISO timestamp (preserving the header comment lines), and pushes a sorted version via auto-merging PR if anything changed. Closes the debt left by HV-071 (`merge=union` driver) — which auto-resolves conflicts but appends without sorting, so entries can drift out of chronological order over time.

## Why
HV-071's `merge=union` is the right call for events.log conflicts (concatenate both sides, no human resolution). The trade-off is that two parallel branches each appending to events.log will produce a log where their entries interleave in *insertion* order rather than *timestamp* order. Single-merge: barely noticeable. Across days of swarm activity: the log becomes harder to follow.

A 30-min cron that re-sorts is the smallest possible fix. No new infrastructure, just one more workflow.

## Done when

### Sort script
- `scripts/sort-events-log.sh` (POSIX) and `.ps1` (Windows):
  - Read `hive/events.log`.
  - Preserve any leading `#` comment lines as-is at the top.
  - Sort the remaining entries by the leading ISO timestamp (lexicographic sort works since ISO 8601 sorts naturally).
  - If the sort changes anything, write back to `hive/events.log` and emit "changed" to stdout. Else "no changes."
  - Exit code 0 in both cases.

### Cron
- `.github/workflows/sort-events-log.yml`:
  - Runs every 30 min.
  - Checks out main, runs the sort script, and if `git status --porcelain` shows changes, commits + opens an auto-merging PR titled "chore: sort hive/events.log (HV-083 cron)."
  - PR auto-merges via the standard flow.

### Verification
- Manual: introduce two out-of-order entries into events.log via two PRs landing back-to-back. Confirm the next cron run produces a PR that re-sorts them. Confirm the auto-merge lands cleanly.
- typecheck + lint + tests + build clean (no source code changes).

## Out of scope
- De-duplication of identical lines. Out of scope; if dupes appear (rare), they're audit-meaningful.
- Sort key beyond the timestamp. Lines with the same timestamp can stay in insertion order; that's fine.
- Sort presence.log too. presence.log entries already age out within 24h via the prune rule (HV-061), so chronological drift is bounded. Skip unless it becomes a problem.

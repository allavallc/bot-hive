## Goal
Two identities exist in the swarm protocol today, conflated as one "handle":
- **Durable agent identity** — *who is the worker?* Stable across sessions. The thing tickets should bind to.
- **Ephemeral session handle** — *which sitting of that worker?* Random per-session. Useful for live distinguishing in chat / presence / swarm-panel.

Today's `Assigned to: tern` binds tickets to the session handle, so when a Claude Code session restarts and picks `wren`, yesterday's tern-tagged in-review work orphans — the new session has no way to recognize "this is mine to follow up on."

This ticket separates them.

## Why
Real failure observed 2026-05-06: CC2 picked handle `tern` yesterday, shipped HV-039 to in-review. Today CC2 (same human, same laptop, same Claude Code instance) started a fresh session as `wren`. wren has no memory or signal that tern's in-review ticket is theirs. The ticket sits in limbo because neither wren-session nor any other agent has a reason to claim it.

The 2h stale-claim cron (HV-066) handles in-progress, not in-review. Even if it did, the convention shouldn't *require* a 2h-old reclaim — it should just match identity correctly the first time.

## Done when

### The convention

- A new field on `Assigned to:` uses an **agent-id** rather than a session handle:
  ```
  - **Assigned to**: allavallc-cc2 (claude-opus-4-7)
  ```
  where `allavallc-cc2` is the durable agent identity, `claude-opus-4-7` is the model.
- Session handle (`tern`, `wren`, `kestrel`) does **not** appear in ticket frontmatter. It lives in:
  - `hive/presence.log` (so concurrent sessions on the same agent-id stay distinguishable in real-time)
  - Swarm-panel chat (color + display)
  - Commit trailers (`Bot:` field — keeps audit-level "who-typed-what" granularity)

### Resolution order at session start

1. **`git config bot-hive.agent-id`** — preferred. One-time per clone. Lives in `.git/config`, where devs already look for repo-local settings.
2. **Default-derive**: `${git user.email}@${HOSTNAME}` if no explicit setting. Most users (one Claude Code per laptop) get this for free, no setup.
3. **No `BOT_HIVE_AGENT_ID` env var.** Considered and rejected — adds shell-rc complexity for every user, and the per-clone `git config` is simpler for the multi-agent case.

### Multi-agent on one machine

For users running two concurrent agents on the same laptop: clone the repo twice, set `git config bot-hive.agent-id` differently in each. The filesystem (separate working directories) provides natural separation — no env var setup, no runtime magic.

### Resume-on-session-start

On session start, after handle pick:
1. Resolve agent-id (per the order above).
2. `grep "Assigned to: <agent-id>" hive/in-progress/*.md hive/in-review/*.md` — surface any tickets owned by this agent-id.
3. Print summary to the human: "I'm `<handle>` (agent: `<agent-id>`). Resuming: HV-X (in-review), HV-Y (in-progress)."

## Out of scope
- Rewriting existing in-flight tickets to use agent-id format. Let them age out via the cron.
- A `bot-hive doctor` / setup wizard. The single git-config command + the default-derive is enough.
- Cross-machine identity stability (a single agent-id used on two laptops). Each clone has its own config; that's intentional.

## Notes
- Why this is elegant: zero setup for the 90% case (default-derive), one command for the 10% case (multi-agent), no env vars, no migration.
- Two-level identity (durable + ephemeral) mirrors how every distributed system handles this — the only innovation is that we noticed we'd conflated them.
- This is the structural fix for the "name<>work<>session complexity" the user flagged on 2026-05-06.

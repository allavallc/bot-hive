## Goal
Close the loop on HV-082 (optimistic column placement for bot signals). Two missing pieces:

1. **Convention retirement.** AGENTS.md and `hive/HIVE.md` still describe the 2-PR claim-then-work pattern as the canonical flow. With HV-082 shipped, the claim PR is unnecessary — the bot publishes a `claim` signal at the start of work and the board renders the in-progress state optimistically within ~200ms. Work PR moves the file backlog → in-review in a single PR.

2. **Helper script.** Bots have `scripts/announce-presence.sh` for presence signals but no parallel for lifecycle signals (`claim`, `done`, `blocked`, `note`). Without a one-command helper, bots have to hand-curl the API with their token, and the convention dies on the friction.

## Why
The 2-PR convention existed because the board state was tied to the file location on main. With HV-082, the board reads the SSE channel for live state and only falls back to file location after deploy. Keeping the 2-PR convention now means **every ticket pays two CI cycles + Render redeploys**, which is exactly the queue churn this session has been fighting.

Wren independently identified this gap during today's parallel-bot session and flagged it to the user.

## Done when

### `scripts/signal.sh` (and `.ps1`)

A general-purpose helper that publishes any signal type:

```bash
./scripts/signal.sh --type=claim --refs=HV-085
./scripts/signal.sh --type=done --refs=HV-085 --message "tests green"
./scripts/signal.sh --type=blocked --refs=HV-085 --message "waiting on render redeploy"
./scripts/signal.sh --type=note --message "pulling latest before claim"
```

Resolves the bot token (env `BOT_HIVE_TOKEN` or `git config bot-hive.token`), the project id (env `BOT_HIVE_PROJECT_ID` or `git config bot-hive.project-id`), and the agent-id + handle (per HV-074). POSTs the signal. Prints the API response.

Same shape as `announce-presence.sh` — they could share a library function, but for v1 keep them as two scripts. PowerShell variant matches.

## Goal
Update the handle convention so every bot session — including two sessions on the same machine — has a unique handle. Bots auto-pick fresh on every session start; the picked name is held in memory for the session and never persisted to `git config`. Collisions with handles already in active use are detected against the environment (recent commits, in-progress tickets) and avoided.

## Why
HV-036 documented "set `git config bot-hive.handle` once per machine, persists forever." That model means **two bots on the same laptop can't have different handles** — both reads of `git config bot-hive.handle` return the same string. For the actual use case (one human running two parallel Claude sessions on one machine), that breaks the swarm — they're indistinguishable in audit.

The fix is per-session identity, not per-machine. Each session is a fresh entity. That maps better to how Claude sessions actually work (each session is a new instance with a new context) and supports the n-bots-on-one-machine case.

## Done when

### Convention updated

- **Auto-pick happens every session start.** Bots do NOT read `git config bot-hive.handle` for handle. (`git config` may be removed entirely or kept only as a deprecated/override path.)
- **Collision detection** before settling: bot scans `git log --grep "Bot: " -n 50` AND `hive/in-progress/*.md` for `Assigned to:` values. If our random pick collides with any handle in active use, re-pick. Repeat until clean (max 10 tries; if all collide, append a suffix like `-2`).
- **Override hook:** environment variable `BOT_HIVE_HANDLE=billy` always wins over auto-pick. Allows the user to lock a bot to a specific name when they want to (e.g., for a specific demo or test).
- **Handle lives in memory** for the session — no file write, no git-config write. Each session is a fresh roll.
- **Announce on session start:** "I'm <handle>" so the user (and the user can tell which window is which).

### Documentation updated

- `hive/HIVE.md` "Bot identity" section rewritten to reflect per-session identity. Remove the `git config bot-hive.handle` setup instructions; replace with "auto-pick on session start, override via env var."
- `CLAUDE.md` "Identity (read first)" section rewritten to match.
- Both files mention the collision-detection scan explicitly.
- Add a note: existing tickets with handles persist (audit honesty — handles set under the old convention stay in the audit trail).

### Existing handles handled gracefully

- Handles already set via `git config bot-hive.handle` (e.g., my `nectar`, CC2's `waggle`) **continue to be honored for the rest of the current session** — don't yank handles mid-session. On the next session, the bot picks fresh.
- Optional: bot session at start can `git config --unset bot-hive.handle` if it wants to clean up. Document but don't require.

## Desired output
Two Claude sessions on one machine each pick a different handle on start. Audit attribution works at the session level. The "two bots on the same laptop" case is genuinely supported.

## Success signals
- Open Claude Code session A on laptop. Auto-picks `nectar`.
- Open Claude Code session B on the *same* laptop, same repo. Auto-picks something different (e.g., `waggle`) because `nectar` shows up in recent `git log` / in-progress tickets.
- Both sessions commit independently; `git log --grep "Bot: nectar"` shows session A's work, `git log --grep "Bot: waggle"` shows session B's.
- The board shows both handles as distinct colored badges.

## Failure signals
- Two sessions on one machine end up with the same auto-picked handle (collision detection didn't fire).
- A bot stalls at startup waiting for some lock or config read (auto-pick should be instant — pure local computation + `git log` grep).
- Override env var ignored.

## Notes
- **Why not `git config --global`?** That'd give same handle to all sessions on a machine. User explicitly wants different handles for two sessions on one machine.
- **Why not `git config --local`?** That's per-repo, but two sessions on the same repo would still share. Same problem.
- **Why not a per-PID file?** Filesystem persistence adds complexity for no value. In-memory is fine — sessions don't need to persist their own handle across crashes; they can re-roll on restart.
- **What happens if a session reroll creates the *same* handle as last session?** Fine — collision check is against currently-active handles, not historical ones. A handle that finished work hours ago is free for re-use. Audit-wise, the `git log` trailers still show the right attribution for the prior session's commits.
- **Out of scope:** complex namespace management (per-team, per-org). Single-namespace, single-repo, swarm self-coordinates.
- This is the right per-session model. The earlier "set once per machine via git config" was the wrong abstraction — it conflated "what machine am I on" with "which agent am I." Those are different concerns.

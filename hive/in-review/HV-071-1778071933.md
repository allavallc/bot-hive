## Goal
Stop hand-resolving merge conflicts on append-only log files (`hive/events.log`, `hive/presence.log`) every time two PRs land back-to-back. Git ships a built-in `union` merge driver that handles "both sides added new lines" by concatenating both — exactly the correct behavior for an append-only log. Two lines in `.gitattributes` and the entire class of friction goes away.

## Why
Even with a single agent, the PR queue lands sequentially. Every PR that touches `events.log` (and there are many — every ticket lifecycle move) goes DIRTY when the previous PR merges, because git's default text merge can't auto-combine appended lines. Manual rebase + resolve cycle ensued every ~10 min during this session.

The append-only contract makes the answer trivial: union both sides. Git already supports this — just declare the file as `merge=union` in `.gitattributes`. No driver script, no setup, no commit-msg hook. Single source of truth.

`presence.log` (HV-061) has the same shape and the same need.

## Done when
- `.gitattributes` adds:
  ```
  hive/events.log merge=union
  hive/presence.log merge=union
  ```
- Future merges where both sides appended to either file resolve to "all lines from both sides," no CONFLICT markers.
- Chronological order may drift by a few entries across merges (the union driver concatenates without sorting). That's acceptable — every line carries an ISO timestamp, so consumers can sort if they need to.

## Out of scope
- Sorting / deduplication — the union driver does neither. Adding sort would require a custom driver script (one-line shell), which is more tooling than this ticket warrants. Out-of-order entries are tolerable; if it becomes a problem, file a follow-up ticket adding a sort pass.
- Other log-shaped files in the repo. Only events.log + presence.log are actively contended.

## Verification
- Manual: create two branches each appending different lines to `hive/events.log`, merge one then merge the other — confirm no CONFLICT.
- This PR itself sits behind several other open PRs that all touch events.log; if it lands cleanly, the convention's working. If it goes DIRTY, that's pre-existing churn (events.log has had conflicts during this very session); after this lands, future similar PRs won't.

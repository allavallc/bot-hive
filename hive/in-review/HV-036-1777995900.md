## Goal
Each bot session has a unique, human-readable handle (e.g., `CC1`, `CC2`, or biology-inspired names like `scout`, `forager`, `queen`) that appears in the `Assigned to:` ticket field, in commit trailers, in `events.log` entries, and on the live board UI. When looking at the board, the human can tell at a glance which bot did what — even when both bots run the same model.

## Why
Today the only bot identity is the model ID (`Model:` trailer). Two bots running the same model — say two `claude-opus-4-7` sessions on two laptops — are indistinguishable. As parallel-bot work scales (FS-007), the human needs a quick visual way to see "CC1 is on HV-031, CC2 is on HV-034" without grepping commit trailers. The board is the user's primary view; without per-bot identity, the swarm is anonymous.

This also closes a swarm-design gap: in nature, each bee/ant has a colony identity but its individual contribution is invisible. In a software swarm, individual identity is cheap and worth surfacing — it lets the human spot a misbehaving bot, attribute work for audit, and build trust by seeing who did what.

## Done when

### Identity source

- Each machine declares its bot handle once. Recommended: a single `git config bot-hive.handle CC1` per machine (or `~/.bot-hive/identity`, gitignored). Bot reads it on session start; if missing, bot prompts the user to set it before claiming any ticket.
- Handle format: short, human-readable, ASCII-only, no spaces. Examples: `CC1`, `CC2`, `scout`, `forager-3`, `tony-laptop`. Max ~20 chars.

### Surfaces

- **`Assigned to:` field** — populated with the handle (e.g., `CC1`). Optional model suffix in parens: `CC1 (claude-opus-4-7)`. Both formats accepted by the parser.
- **Commit trailers** — add `Bot:` line alongside existing `Model:` and `Trigger:`. Format: `Bot: CC1`. Required for ticket-lifecycle commits, optional elsewhere.
- **`events.log`** — every event line ends with the originating bot handle. Format: `2026-05-05 11:42 HV-031 done HV-032,HV-033 unblocked CC1`.
- **Board UI** — ticket cards render the handle in a visible badge or footer. Distinct color per handle is nice-to-have, not required.

### Documentation

- `bot-hive/CLAUDE.md` — short section on declaring identity (`git config bot-hive.handle ...`), what handles look like, where they appear.
- `hive/HIVE.md` — same convention in format-neutral terms.

### Verification

- Two bots on two machines with different handles claim different tickets. Board shows both handles distinctly.
- A bot without a handle configured tries to claim a ticket — bot stops and tells the user "set `git config bot-hive.handle <name>` first."
- Vitest: ticket parser extracts handle from `Assigned to:` field correctly for both formats (`CC1` and `CC1 (claude-opus-4-7)`).

## Desired output
The user can glance at the board and immediately see "CC1 is working FS-007, CC2 is working FS-008" — no grep, no log dive. Audit trails carry the handle so post-hoc analysis ("who broke main on Tuesday?") is one `git log --grep` away.

## Success signals
- Two sessions running same model on two laptops are visually distinguishable on the board.
- A user reading recent commits can attribute each one to a specific bot session, not just a model name.
- A new bot joining the swarm just runs `git config bot-hive.handle <name>` once and is fully identified everywhere.

## Failure signals
- Handles drift (CC1 commits as "cc1" sometimes, "CC1" other times). Convention: case-sensitive but normalize on display.
- A bot operates without a handle and ticket attribution is empty.
- Board UI renders handles too quietly (small grey text) and the user can't actually see them at a glance.

## Tests
- Vitest: parser extracts handle correctly from `CC1`, `CC1 (claude-opus-4-7)`, and bare model strings (backward compat — old tickets just show model).
- Manual: end-to-end — two laptops, two handles, different tickets, board renders both visibly.

## How to test
1. On laptop A: `git config bot-hive.handle CC1`. Confirm bot reads it and uses it on next claim.
2. On laptop B: `git config bot-hive.handle CC2`. Same check.
3. Each bot claims a different ticket. Inspect the moved files — `Assigned to:` shows the right handle.
4. Open the board on prod. Both tickets visibly attributed to different handles.
5. `git log --grep "Bot: CC1"` returns CC1's commits only. Same for CC2.

## Notes
- Out of scope: avatar/icon per bot (cosmetic), capability declarations per bot (deliberately rejected by the swarm model — any bot can do any work).
- Out of scope: rotating/changing a bot's handle mid-life. Set once per machine; if changed, recent history still shows the old handle (audit honesty).
- The biology-inspired naming (scout, forager, queen) is optional flair — bots don't actually behave differently based on name. CC1/CC2 is fine. Pick whatever's memorable.
- This was identified as a gap during the first parallel-bot run on 2026-05-05 — both CC1 (claude-opus-4-7) and CC2 (claude-sonnet-4-6) happened to use different models so could be distinguished, but two same-model sessions would have been invisible to each other and to the human.

## Resolution

- **Identity source convention** documented in `hive/HIVE.md` (new "Bot identity" section) and `CLAUDE.md` (new project root file). Bots set their handle once per machine via `git config bot-hive.handle CC1` and read it on session start.
- **`Bot:` commit trailer** added to the provenance trailer convention in `HIVE.md`, alongside existing `Model:` and `Trigger:`. Example block updated, audit query example added (`git log --grep "Bot: CC1"`).
- **`Assigned to:` field** accepts both `CC1` and `CC1 (claude-opus-4-7)` formats. The board UI extracts and displays just the handle.
- **Board UI rendering** (PR #1, merged): each ticket card now shows the bot handle as a colored badge in the meta row alongside the FS badge. The badge color is computed via `robotColor(handle)` — same hash used by `RobotMascot`, so the walking-robot mascot and the badge match. `extractHandle()` helper strips the optional `(model)` suffix.
- **Source-vs-coordination split dogfooded**: `HIVE.md` + `CLAUDE.md` edits committed direct to main (coordination metadata); `board.client.tsx` + `board.module.css` edits went on branch `hv-036-board-handle-display` → PR #1 → squash-merged.
- **Verification**: typecheck + lint + 20/20 tests + build all green at every step.
- **Out of scope (deferred):** `events.log` integration (event log doesn't exist yet — comes in HV-031); enforcement that a missing handle blocks ticket claims (documented as a rule, not yet runtime-enforced).

## Resolution (round 2 — after rejection)

- **Auto-naming convention** documented in `hive/HIVE.md` and `CLAUDE.md`: bots without a handle pick a random word from a 26-name curated list (bee/animal/swarm-themed) on session start, save via `git config bot-hive.handle <name>`, then announce "I'm <name>" to the user. User can override anytime.
- **My handle is now `nectar`** — picked at random from the list when I cleared the forced "CC1" value. HV-036's `Assigned to:` updated to `nectar (claude-opus-4-7)`.
- **Badge skip for bare model IDs:** PR #2 (squash-merged). `extractHandle()` now returns `undefined` when input matches `^(claude|gpt|gemini|llama|mistral|qwen|grok)\b`. Legacy tickets with `Assigned to: claude-opus-4-7` show no badge; tickets with real handles render the colored badge as designed.
- **Test smell discovered, scoped out:** during verification, observed one transient test failure (1/20 once across many runs). Investigation surfaced `Date.now()` in test data and a lack of test isolation. Fix is real architecture work (transactional rollback per test) — filed as HV-037 to address properly rather than band-aid here.
- **Verification round 2:** typecheck + lint + 20/20 tests + build all clean across PR #2 and the doc updates.

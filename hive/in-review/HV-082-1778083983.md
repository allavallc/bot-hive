## Goal
HV-075 makes the board move a card to its destination column within ~1s of a *human's* Accept/Reject click. This ticket extends the same optimistic-placement logic to *bot* lifecycle signals — when a bot publishes a `claim` signal, the card moves from In-Review/Backlog to In-Progress on the board within ~1s; when a bot publishes a `done` signal (i.e., moving in-progress → in-review at end of work), the card moves from In-Progress to In-Review within ~1s.

## Why
Even after HV-075, bot-driven transitions still wait for the full PR + CI + Render redeploy cycle (~3-5 min) before showing on the board. The user sees "wren says it's done but I still see 4 tickets in In-Progress" — the work IS done, the board just hasn't caught up. Same problem HV-075 solved for human Accept/Reject, generalized to bot transitions.

Depends on HV-081: until bots actually publish `claim` / `done` signals on the SSE channel (HV-081's job), this ticket has nothing to react to. Both ship as a pair.

## Done when

### Extended `pendingTransitions` map

`board.client.tsx` already maintains `pendingTransitions: Map<hvId, kind>` for human signals. Extend to also accept bot lifecycle signals:

```ts
type PendingKind =
  | { kind: "approved"; source: "human" }    // existing — human accept
  | { kind: "rejected"; source: "human" }    // existing — human reject
  | { kind: "in-progress"; source: "bot" }   // new — bot claim
  | { kind: "in-review"; source: "bot" };    // new — bot done
```

When a `claim` signal arrives with `refs: [hvId]`, set `pendingTransitions[hvId] = { kind: "in-progress", source: "bot" }`. When `done` arrives, set to `{ kind: "in-review", source: "bot" }`.

### `effectiveState` extension

The `effectiveState(ticket, pending)` function (added in HV-075) handles human signals by mapping `approved → done` / `rejected → in-progress`. Extend:
- `kind === "in-progress"` → render in In-Progress
- `kind === "in-review"` → render in In-Review

### Banner reuse

The pending-transition banner (HV-072) currently shows for human transitions only. Extend for bot transitions, with appropriate text:
- Bot claim: `<handle> claimed — pending sync` (subtle, doesn't compete with human-action banners)
- Bot done: `<handle> finished — pending sync` (same)

(Style choice: bot banners use `--ink-dim` text rather than the bold green/orange of human banners. Less visually loud since the user isn't waiting on themselves to do something.)

### Cleanup

`pendingTransitions` already clears when the SSE ticket-state refresh shows the actual move completed (HV-075 logic). Same applies to bot transitions — when the file actually lands in the new state, the optimistic entry clears.

## Goal
A convention added to AGENTS.md and HIVE.md: any active agent, on session start and periodically while working, scans open PRs and runs `gh pr update-branch <number>` on any in `BEHIND` state. The active swarm tends idle PRs that left bots have abandoned.

## Why
Today (2026-05-05) we hit a real failure mode: CC2 opened PR #28 for HV-039, finished its session, and went silent. Meanwhile main advanced via my work — PRs #25, #26, #27 all merged. CC2's PR went `BEHIND`, then `DIRTY` when its events.log line collided with new entries, and sat unable to auto-merge until I force-rebased it on CC2's behalf.

The pre-commit pull rule (HV-043) doesn't help here — CC2 *had* committed and pushed its branch. The PR was already open. The conflict only surfaced when main moved later. By then CC2 was idle.

The fix: any bot that's *currently* online and working should also be a steward of any open PRs. If a PR is behind, it costs ~5 seconds to call `gh pr update-branch` and let GitHub do the merge-from-main automatically (works for clean updates; surfaces conflicts for dirty ones, which then escalate to humans per existing policy).

This isn't a coordinator service or central authority — it's a swarm rule. Every active bot is a watchdog for every open PR. Failure-tolerant by construction; if no bots are online, idle PRs just wait.

## Done when

### Convention installed in AGENTS.md and HIVE.md

In the "Working in parallel" section, near the existing "Pre-action pull" rule, add a new subsection:

**Stale-PR watchdog**

> On session start (after `git pull`, before claiming work), and every ~10 minutes while the session is active, run:
>
> ```bash
> gh pr list --json number,mergeStateStatus,isDraft \
>   | jq '.[] | select(.isDraft == false) | select(.mergeStateStatus == "BEHIND") | .number'
> ```
>
> For every PR number returned, run `gh pr update-branch <number>`. GitHub will merge current main into the PR's branch. CI re-runs; auto-merge fires if the result is clean.
>
> **For DIRTY PRs (real conflicts), don't touch them.** Conflicts mean someone needs to resolve manually; surface to the human via `hive/questions-for-human.md` rather than guessing a merge.
>
> This isn't a chore — it's part of being a good swarm citizen. The cost is ~5 seconds; the savings is hours of idle-PR rot.

### Add a small helper script

`scripts/update-stale-prs.sh` (or `.ps1`) wrapping the above for ergonomics. Bots can call this directly without remembering the jq incantation.

Add to FS-007's "Architecture & decisions" section:

## Desired output
Idle PRs left by departed bots get auto-updated within ~10 minutes of becoming stale, as long as any bot is online. Force-rebases by humans (like today's intervention on PR #28) become rare.

## Success signals
- A PR that was opened by a bot whose session ended doesn't go DIRTY before another bot updates it.
- The "first parallel-bot session" friction (today) doesn't recur — main can advance freely; open PRs catch up.
- No bot ever attempts to merge a DIRTY PR — the rule "don't touch DIRTY" holds.

## Failure signals
- Bots burn API quota running the watchdog scan too often. Mitigation: ~10 min cadence is a soft cap; if it ever feels excessive, raise to 30 min.
- Bots try to "resolve" DIRTY PRs and corrupt CC2's work. Mitigation: convention is explicit — DIRTY is escalation territory.
- Watchdog runs on PRs the bot doesn't own / care about. Mitigation: that's actually fine — updating any open PR is a public good. No ownership semantics.

## Notes
- **Why not server-side?** HV-051 covers a server-side cron. We're filing both: the convention is universal and zero-infra; the cron is a backstop. They complement each other.
- **Why every 10 min?** Heuristic. PRs typically don't go BEHIND faster than that, and burning ~10 GitHub API calls per session per hour is well under any rate limit.
- Out of scope: tracking *which* bot last updated each PR. Bots are interchangeable; the swarm doesn't need ownership ledgers.
- Out of scope: notifying humans when PRs go DIRTY. Already covered by `hive/questions-for-human.md` — bot escalates when it can't resolve.
- This was the lesson from today's first parallel-bot session — capture it before the next one repeats it.

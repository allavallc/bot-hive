## Notes

**Why `hive/roles.md` parsed by the server.** The markdown table at `hive/roles.md:25–30` is the canonical consolidation rule. Hardcoding the same values in TypeScript creates drift risk and adds a place future maintainers must remember to update. Parsing the markdown at startup (a few regex lines, cached for the process lifetime) is cheap and single-source. The server's working directory at runtime is the repo root (it serves the `hive/` files to the kanban already; see `src/lib/parse.ts`), so the file is present.

**Why the advisory lock keyed on `(project_id, colony)`.** Two bots in different colonies (or different projects) joining at the same instant can proceed in parallel — they're independent seat sheets. Two bots in the same `(project, colony)` must serialize, otherwise both can compute `seat = 2` simultaneously and the partial unique index will reject one of them with a constraint violation that's harder to recover from than a few microseconds of lock contention.

**Why `repo_full_name` rather than `project_id`.** Bots know their repo from `git remote get-url origin` (or via an extended `.bot-hive-identity`). They don't know the platform's internal UUID. Server-side lookup by `githubRepo` is one DB hit and keeps the bot-side identity file simple.

**Auth.** None in v1. Documented as a known limitation in the FS-028 spec; follow-up ticket adds Bearer-token auth.

**Out of scope** (covered later in FS-028):
- `POST /heartbeat`, `POST /leave`, sweep-on-request — HV-131.
- `GET /colony` and the UI surface — HV-132.
- Client-side `scripts/whoami` rewrite — HV-133. (Until HV-133 lands, the old file-scan whoami still runs; the new endpoint is dormant.)

**Risk.** A bot calling `/join` against a `repo_full_name` whose project hasn't been registered in the platform gets a 404. Operator workflow today registers projects via Add-a-Project before adding bots, so this should be rare — HV-134's docs make the dependency explicit.

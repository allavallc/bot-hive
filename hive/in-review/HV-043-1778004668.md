## Goal
Bots have a way to know when the repo has been updated upstream during their session — without polling on every action — so they can `git pull` before continuing and pick up new conventions, new tickets, or other agents' work without operating on a stale clone.

## Why
Today, bots `git pull` on session start (per the swarm protocol) and trust their local clone for the rest of the session. If a session runs for an hour and another agent (CC1, CC2, the human) pushes updates mid-session, this bot is operating on stale state. Specific failure modes:

1. **New convention added to HIVE.md mid-session.** Bot doesn't know about it; commits in old format; audit trail gets noisy.
2. **A ticket this bot might have wanted to claim got created.** Bot can't see it without re-pulling.
3. **A ticket this bot is working on got deleted/moved by another agent.** Bot keeps editing the old path; commit fails or worse — succeeds against the wrong file.
4. **The conflict-response policy or other rules updated.** Bot acts on outdated rules.

The current mitigation is "remember to `git pull` before any commit." Sometimes this happens; sometimes it doesn't. The conventions assume the bot is disciplined; nothing forces correctness.

## Done when

A bot has a cheap, reliable way to detect "the repo has changed since I last pulled" without polling the remote on every action. Possible mechanisms (to be evaluated, not all required):

- **Option A: Pre-commit pull.** Bot always `git pull --rebase` immediately before any commit. Cheap (one network round-trip per commit), guarantees freshness. Already partially in the conventions; would just be tightened to "always, no exceptions."
- **Option B: Heartbeat file.** A `hive/heartbeat.txt` (or similar) that updates with the last-push timestamp on every commit. Bots check the file's mtime before any action; if newer than their session start, they pull. Pro: no network round-trip per check. Con: only signals via a commit, not arbitrary events.
- **Option C: GitHub webhook → bot endpoint.** Push events trigger a webhook that pokes active bot sessions (via Slack/Discord/some bus). Real-time. Con: requires real-time infrastructure that the swarm protocol explicitly rejects.
- **Option D: Polled `git fetch`.** Bot `git fetch`es every N seconds (e.g., 60s) in the background; if `origin/main` advances past local `main`, bot is notified to pull before next commit. Con: adds a daemon/timer, drift from the "files-and-git only" model.

Done when:
- One of the options above (or a hybrid) is chosen, documented in `HIVE.md` "Working in parallel," and adopted by all sessions.
- The choice is justified against the substrate-vs-conventions framing — same convention should work as the substrate evolves.
- Updated in `CLAUDE.md` for project-specific concretization.
- Acceptance test: deliberately push a change while a bot is mid-session; the next bot action should detect the staleness and pull before proceeding.

## Desired output
A bot that has been running for an hour, when prompted to do anything, knows whether its local clone is current. If stale, it pulls before acting. No more "operated on rules from an hour ago" failures.

## Success signals
- Two bots running concurrently never operate on stale state for more than N seconds (where N is whatever pull cadence is chosen).
- A new convention added to HIVE.md by one bot is honored by another within the next session-action cycle.
- No new ID collisions or stale-claim issues caused by missed pulls.

## Failure signals
- Bot pulls before every action even when nothing has changed (wasted round-trips). Pre-commit pull (Option A) would have this — fine if cheap, problematic if frequent.
- Bot has a stale signal source (heartbeat file, fetch cache) that disagrees with the actual remote state.
- The chosen mechanism requires infrastructure beyond git (webhook server, Slack bus, etc.) — that violates the swarm protocol's "files-and-git only" principle.

## Tests
- Manual: open two sessions. In session A, push a HIVE.md change. In session B, do something that should pull (per the chosen mechanism); confirm the change is now visible.
- Manual: push a new ticket from session A. Session B should be able to claim it without manual `git pull`.

## Notes
- **My current lean: Option A (pre-commit pull).** It's the simplest, lives in the existing convention, no new file or daemon. The cost (one network round-trip per commit) is negligible at swarm scale.
- Option B (heartbeat file) is a nice complement — bots can avoid pre-commit pull when the heartbeat says the remote hasn't moved. Optimization, not core.
- Option C (real-time webhook) is rejected for the same reason the swarm protocol rejects coordinator services and message brokers — adds infrastructure with no current need.
- Option D (polled fetch) drifts from the "files-and-git only" model; rejected unless A and B prove insufficient at scale.
- Out of scope: bots in adopter repos (other repos using the hive format) detecting bot-hive product updates. That's a separate concern — versioned spec, vendoring, or adopter responsibility. Not part of this ticket.
- Filed because: question came up during the parallel-bot session on 2026-05-05 — "do we have any kind of signal on the repo so that if we update bot-hive that a bot will 'know' they need to download the repo?" Answer was no. This ticket is the future fix.

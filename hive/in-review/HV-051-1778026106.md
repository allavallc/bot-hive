## Goal
A scheduled GitHub Actions workflow that runs every 10 minutes, scans open PRs, and triggers `gh pr update-branch` on any in `BEHIND` state. Acts as a server-side backstop to HV-050's bot-side watchdog convention — even if no bots are online, GitHub itself keeps PRs current.

## Why
HV-050 installs the convention "any active bot updates BEHIND PRs." That works when bots are online. When they're not (e.g., overnight, or between work sessions), open PRs left in BEHIND state sit indefinitely.

A cron-driven GitHub Actions workflow is the simplest server-side fix. No new infrastructure — uses Actions we already pay for via the `ci.yml` workflow. Runs at a fixed cadence, hits the same `gh api` we'd run manually, requires no bot.

## Done when

- New file `.github/workflows/update-stale-prs.yml`:
  - Schedule: `cron: "*/10 * * * *"` (every 10 minutes).
  - Permissions: `pull-requests: write` (needs to call `pulls/{number}/update-branch`).
  - Steps:
    1. List open non-draft PRs with `gh pr list --json number,mergeStateStatus,isDraft`.
    2. Filter to `mergeStateStatus == "BEHIND"`.
    3. For each, call `gh pr update-branch <number>`. Continue on errors (a DIRTY PR will return an error — that's fine, skip and keep going).
- Test the workflow locally: open a no-op PR, let main advance, wait 10 minutes, confirm the PR auto-updates.

## Desired output
Open PRs never stay BEHIND for more than 10 minutes, regardless of whether bots are online.

## Success signals
- Manual smoke test: open PR, let main advance, wait. PR updates within 10 min without human intervention.
- Bot sessions starting a new task don't have to do their own watchdog scan unless they want to (HV-050 still applies as a "be a good citizen" rule, but it's now redundant with the cron).

## Failure signals
- The cron runs hit GitHub's secondary rate limits. Mitigation: cadence is generous (10 min); even with many PRs open we're well under any limit.
- The cron tries to update a PR that's actually DIRTY (race between BEHIND check and update call). Mitigation: GitHub's API returns an error for that case; the workflow logs and continues.
- The cron runs against PRs the user doesn't want auto-updated (e.g., draft PRs). Mitigation: filter is explicit (`isDraft == false`).

## Tests
- Manual: open a non-draft PR, push a no-op commit to main, wait 10 minutes. PR should auto-update.
- Manual: open a draft PR, same setup. Confirm draft PRs are skipped.
- Manual: open a PR with a real conflict (DIRTY). Confirm the cron skips it.

## How to test
1. Land HV-051 (this PR).
2. Open a no-op test PR. Wait for it to be `MERGEABLE`.
3. Push a commit to main from another branch. Wait 10 min.
4. Confirm the test PR transitioned BEHIND → MERGEABLE → auto-merged.

## Notes
- **Why a cron and not a webhook?** Push-to-main webhook would be more responsive (instant), but it's also more wiring. Cron is a single yaml file. We can upgrade to webhook later if 10-min latency feels slow.
- **Permissions:** the workflow needs `pull-requests: write` to call update-branch. Default `GITHUB_TOKEN` should suffice (it has read+write on its own repo).
- **Cost:** GitHub Actions free tier includes 2,000 cron-minutes/month. At 6 runs/hour × 24 hours × 30 days = 4,320 runs/month, each ~10 sec ≈ 720 minutes. Comfortable margin.
- Out of scope: smarter scheduling (only run if there are open PRs). Premature optimization; flat cron is fine.
- Out of scope: notifications when DIRTY PRs are detected. The convention has bots / humans handle that.

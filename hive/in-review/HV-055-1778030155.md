## Goal
When a human clicks **Accept** or **Reject** on an in-review ticket, a visible "Approved" or "Rejected" indicator appears on the card immediately and stays until the underlying PR merges + deploys (which moves the ticket to its new column). Closes the 3–5 minute void between click and visible state change.

## Why
Today's flow:

1. Human clicks Accept → API creates a PR moving the ticket to `done/`
2. CI runs (~2 min)
3. Auto-merge fires
4. Render redeploys (~2 min)
5. Board re-renders with the ticket in **Done**

Between steps 1 and 5 — a 3–5 minute window — the user has **no visual confirmation** that anything happened. The card still looks identical. They wonder: did my click register? Did it work? Should I click again? In testing today, the user clicked Accept and waited, unsure if it succeeded.

The fix is a transient indicator on the card itself — a small "Approved (pending merge)" or "Rejected (pending merge)" badge — visible the moment the click fires, persistent until the deploy lands.

## Done when

### Visual indicator

- The Accept/Reject API response carries the new pending-transition state back to the client.
- The board's data model adds an optional `pendingTransition: "approved" | "rejected"` field per ticket.
- Cards render a small badge in the meta row when `pendingTransition` is set:
  - **Approved** — green background, white text, e.g., `✓ Approved (pending merge)`
  - **Rejected** — red/orange background, white text, e.g., `↻ Rejected (pending merge)`
- The badge is visually distinct from existing FS / handle / priority badges (different placement or shape) so it's immediately legible.

### State source

The pending state needs to survive across:
- Multiple users viewing the same board simultaneously (one user's accept should be visible to the other within seconds)
- The user closing and re-opening the panel (the badge should still show)
- Accidentally double-clicking Accept (should be idempotent — second click is a no-op)

Implementation approaches (decide during build):

- **Option A: server-side in-memory store.** API endpoint records pending transitions; SSE pushes them to all connected clients; badges clear when the underlying ticket-state SSE refresh shows the move completed.
- **Option B: real-time signals (HV-047 channel).** Accept/reject endpoint publishes a `note`-type signal with `{ ticketId, transition: "approved" | "rejected" }`; board listens and renders. Cleaner — leverages the channel we already built. Recommend this path.
- **Option C: ticket-file field.** API writes a `**Pending transition:**` field on the in-review file; the next git push (the actual move) clears it. Survives process restart. But adds a write step + clutters the ticket file. Don't.

### Cleanup

- The pending state is **automatically cleared** when the underlying ticket state moves (the file is on its new path). Implementation: when the board's existing ticket-list SSE refresh shows the ticket in a new column, drop any `pendingTransition` for that ticket.
- The pending state has a hard timeout (e.g., 10 minutes). If the deploy doesn't land in that time, the badge clears with an "❌ Action failed — try again" message instead of staying stuck.

### Idempotency

- Clicking Accept twice on the same ticket: second click returns 409 Conflict (already in pending state) or just no-ops; UI shouldn't fire a second action.
- Same for Reject.

### Verification

- Manual: open the board on two browsers (or two tabs). Accept a ticket on browser A. Confirm the "Approved (pending merge)" badge appears on **both** browsers within ~1 second.
- Manual: wait through the deploy cycle. Confirm the badge disappears when the ticket lands in its new column.
- Manual: deliberately stall the PR (close it without merging). Confirm the badge clears after 10 min with "Action failed."
- typecheck + lint + tests + build all clean.

## Desired output
A user clicks Accept. Within ~200ms, a green "Approved (pending merge)" badge appears on the card. The badge stays for the next 3–5 minutes as the PR runs CI and Render redeploys. Once the deploy lands, the badge disappears and the ticket appears in the Done column. Zero ambiguity about whether the click registered.

## Success signals
- No more "did my click work?" doubt during the wait window.
- A second user watching the same board sees the same indicator at near-real-time.
- Idempotency holds — double-clicking doesn't create two PRs.

## Failure signals
- Badge doesn't clear after the underlying state change — visual stuck-ness.
- Badge appears on tickets the user *didn't* act on (some kind of state leak across cards).
- Badge persists past the timeout without showing the failure state.
- A real failure (CI fail, etc.) doesn't surface — user is left wondering forever.

## Tests
- Manual end-to-end (the verification list above).
- Possibly a vitest test for the cleanup logic if it ends up complex.

## How to test
1. Land HV-055.
2. Open the board, find an in-review ticket.
3. Click Accept. Confirm "Approved" badge appears on the card immediately.
4. Open the same board in another tab. Confirm the badge appears there too within ~1s.
5. Wait through the deploy. Confirm the ticket moves to Done and the badge disappears.
6. Try Reject on a different ticket. Same flow but with the "Rejected" badge style.

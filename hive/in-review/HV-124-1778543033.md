## Goal

`my-work.sh` (and `.ps1`) detects "code merged but ticket file still in-progress" on every cycle and surfaces it as a top-of-output warning. Bot reads its own work-decision output; the warning is unmissable.

## Why this over a CI gate

- Server-side CI gate would also work but couples the workflow to GitHub Actions and adds a per-PR check that has to be maintained.
- This stays inside the bot's own session loop. Self-correcting within one work cycle. No new infra, no new CI surface.
- Rubric prose alone has been tried and slips through in practice (HV-075, HV-113). A scripted check is the durable fix.

## Concrete check

For every ticket in `hive/in-progress/` whose `Assigned to:` matches the running bot:
1. Get the ticket's HV id (e.g. `HV-113`).
2. Look at recent commits on the local `main` branch (or `git log` since branch base) for messages referencing the HV id.
3. If a commit referencing this ticket has merged AND the ticket file is still in `hive/in-progress/` → emit a warning.

Warning format (top of my-work output, before any other section):

```
⚠ HV-XXX: code merged but ticket file still in hive/in-progress/.
  Run: ./scripts/in-review.sh HV-XXX
  (do this BEFORE picking your next ticket)
```

Multiple warnings stack if the bot has multiple stuck tickets.

## Done when

- [ ] `scripts/my-work.sh` and `.ps1` perform the check on every invocation
- [ ] Stuck-ticket warnings render at the top of output (before "your in-progress" section), each with `⚠` prefix and the exact `in-review.sh` command to run
- [ ] No warning if the bot has no in-progress tickets, or all are clean
- [ ] One e2e test: claim a ticket, commit + merge code without running in-review.sh, run my-work.sh → warning appears with correct ticket id
- [ ] One e2e test: claim a ticket, run in-review.sh → no warning

## Out of scope

- Auto-running in-review.sh from my-work.sh (too magical; bot should still acknowledge + run explicitly)
- A CI/server-side gate (filed separately if we want belt + suspenders later)
- Detecting same gap on tickets in in-review/ that should be in done/ (different rubric path; could be a follow-up)

## Goal
The human can reject an `in-review` ticket directly from the board UI (or from a chat message to a bot), trigger the bot to pick the work back up, and capture the rejection reason in the audit trail. Today rejection requires the human to either edit the ticket file by hand and `git push`, or describe the rejection in chat and hope a bot is present to commit it.

## Why
The acceptance loop is the human's primary point of control over the swarm. Today:

- **Acceptance** is mostly silent — human says "approved," a bot moves the ticket to done, the audit trail records it.
- **Rejection** is friction-heavy — the convention says "move ticket back to in-progress with `Rejected by` / `Rejection reason` fields," but the *mechanism* for the human to do this is undocumented and de facto requires a bot to be running. If no bot is online, the rejection sits in chat with no durable record.

Either path produces a real audit gap. A user-friendly flow puts rejection on equal footing with acceptance: one click on the in-review card, type a reason, the bot sees it on its next pull and re-claims.

## Done when

### UI surface

- The board's modal (HV-039) shows two action buttons for any ticket in `in-review`: **Accept** and **Reject**. Visible only to authenticated users with write access to the underlying repo (so randos can't reject random tickets).
- **Reject** opens a small dialog: free-text `Rejection reason` input + Confirm/Cancel buttons.
- On Confirm: the client posts to a new endpoint `POST /api/projects/[id]/tickets/[hv-id]/reject` with `{ reason: string }`. The server:
  1. Validates the user has GitHub repo access (existing `userHasRepoAccess` helper).
  2. Edits the ticket file: sets `Rejected by`, `Rejected`, `Rejection reason` fields.
  3. Moves the file from `hive/in-review/` back to `hive/in-progress/`.
  4. Appends to `hive/events.log`: `<ISO> <hv-id> rejected <handle-or-human>`.
  5. Commits to a new branch (`reject-<hv-id>-<timestamp>`), opens a PR with auto-merge.
  6. Returns the PR URL to the client.
- The modal shows "Rejection submitted (PR #N)" with a link, then closes when the PR auto-merges.

### Backend mechanics

- New API route `POST /api/projects/[id]/tickets/[hv-id]/reject` per above.
- Auth: same `userHasRepoAccess` gate as the rest of the project routes.
- Commit author: the human's GitHub identity (from their session), not a bot handle. This is the one case in the audit trail where the actor is genuinely the human, not an agent.
- Commit message format:
  ```
  HV-XXX: rejected — <reason summary, max 80 chars>

  <full reason if longer>

  Rejected-by: <github username>
  Trigger: HV-XXX rejected
  ```
- The PR auto-merges on green CI (same flow as bot PRs).

### Convention update

- AGENTS.md and HIVE.md get a short paragraph: "Rejections happen on the live board — see `Reject` button on in-review cards. The board commits the rejection on the human's behalf via PR. Bots picking up after rejection see the ticket back in `in-progress/` with the rejection fields populated; they re-read the rejection reason and adjust."
- HIVE.md "Provenance trailers" section: document that human commits use `Rejected-by:` (with their GitHub username) instead of `Bot:` — clarifies that the human is the author of this specific kind of commit.

### Bot-side reaction

- Bots picking up a rejected ticket (status: in-progress, with `Rejected by` populated) should:
  1. Read the rejection reason carefully — it's the spec for the next iteration.
  2. Append to `events.log`: `<ISO> <hv-id> reclaimed-after-rejection <handle>`.
  3. Treat it as a normal in-progress ticket from there.

This bot-side guidance lives in AGENTS.md "Reporting status" / nearby sections.

### Scope decisions

- **The Accept button is also wired** as part of this ticket, since the implementation cost is similar and a half-built UX is worse than no UX. Acceptance moves the ticket from `in-review/` to `done/` with `Verification: human-reviewed` populated.
- A "Comment" path (human leaves a question without rejecting) is **out of scope** — that's `hive/questions-for-human.md`-style escalation in the other direction; can be a follow-up ticket if needed.

## Desired output
A human watching the board sees a card land in In-Review with a slide-and-glow (HV-045). They click the card, modal opens (HV-039), they read the work, they click **Reject**, type "the modal isn't keyboard-trappable, focus escapes after Tab x3," click Confirm. ~3 seconds later the ticket is back in In-Progress with the rejection reason captured in the file. The next bot to claim it reads the rejection reason and starts iterating. Total human friction: one click + ~30 seconds of typing.

## Success signals
- Rejection takes <30 seconds of human time, including typing the reason.
- Rejection reason is durable (in the ticket file + commit message + events.log) — searchable later via `git log --grep "rejected"`.
- Bots reclaiming after rejection consistently address the rejection reason rather than re-doing the same broken work.
- No human ever has to manually edit a hive/ ticket file via the local checkout for rejection again.

## Failure signals
- The reject dialog is too friction-y (long form, multi-step) and humans avoid it, falling back to chat.
- Rejections happen but the bot reclaiming the ticket doesn't notice the rejection reason — it just builds the same thing again. Bot-side guidance needs to be sharper.
- Race conditions: two humans both reject the same ticket at the same time, or one human rejects while a bot is already pushing an "in-review accept." Tactic: the existing PR + branch protection + auto-merge handles ordering; whoever's PR merges first wins, second has to rebase.

## Tests
- Manual: open a ticket in In-Review on prod. Click Reject. Type a reason. Confirm. Verify a PR opens, CI runs, auto-merge fires, ticket lands in In-Progress with rejection fields populated. Confirm `events.log` has the event.
- Manual: same with Accept — ticket lands in Done with `Verification: human-reviewed`.
- Manual: a non-collaborator (logged in as a user who doesn't have GitHub access to the underlying repo) tries to call the API directly via curl. Verify it returns 403.
- Vitest: API route returns 200 + commits the file change when the user has access; 403 when they don't.

## How to test
1. Pick a ticket in In-Review (e.g., HV-039 itself if it's still there at test time).
2. Click into the modal. Confirm Reject and Accept buttons are visible.
3. Click Reject. Type a non-trivial reason. Confirm.
4. Watch for the auto-opened PR. Wait for it to merge (~2 min).
5. Confirm the board now shows the ticket in In-Progress, with the rejection reason in the file.
6. (Bot-side) Have a bot claim the rejected ticket. Confirm it reads the rejection reason and adjusts.

## Notes
- This ticket is the **acceptance-loop completion** — Bot Hive's review cycle has been bot-only-driven so far; this gives the human first-class control over rejecting work without requiring git/file knowledge.
- High priority because every rejection right now is a friction point that pushes humans to skip the audit trail. The longer this lands, the more rejections get captured only in chat.
- Out of scope: rejection comments / threads (multi-message rejection-and-iteration). One-shot reject-with-reason is the v1.
- Out of scope: "soft reject" (request changes without bouncing the ticket all the way back to in-progress). Could be a future ticket if the binary accept/reject feels too coarse.
- Out of scope: rejection notifications to the original bot (email / Slack / etc.) — the bot picks up via the next session's events.log read.

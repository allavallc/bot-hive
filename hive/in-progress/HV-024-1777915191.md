## Goal
Wire prod URLs into GitHub on both apps so the deployed Bot Hive can complete sign-in (OAuth App) and receive webhooks (GitHub App).

## Why
After HV-023 the app is reachable at a public URL but GitHub still bounces every OAuth callback to localhost and still posts every webhook to the smee proxy. Until these URLs are updated, prod is effectively unreachable.

## Done when
- **GitHub OAuth App — separate prod app, not appended to the existing one.** OAuth Apps allow only **one** Authorization callback URL (single field, no list), so a multi-environment setup needs separate apps:
  - New OAuth App `Bot Hive (Prod)` registered at github.com → Settings → Developer settings → OAuth Apps → New OAuth App.
  - Homepage: `https://<render-prod-url>`. Authorization callback URL: `https://<render-prod-url>/api/auth/callback/github`. Device Flow off.
  - New `GITHUB_CLIENT_ID` + `GITHUB_CLIENT_SECRET` set in Render env vars (overwriting the dev placeholders set in HV-023).
  - Local `.env` keeps the original (dev) OAuth App credentials. Local-dev sign-in keeps working unchanged.
- **GitHub App — repoint the existing app at prod.** GitHub Apps also have a single webhook URL field, so the existing app is repointed (not duplicated). Acceptable trade-off because the GitHub App's webhook is the only field that affects local dev:
  - **Webhook URL** changed to `https://<render-prod-url>/api/github/webhook`. (Smee no longer receives webhooks; local-dev webhook flow breaks until we split into separate dev/prod GitHub Apps in a future ticket.)
  - **Setup URL** changed to `https://<render-prod-url>/projects/install/callback`.
  - **Callback URL** changed to `https://<render-prod-url>/projects/install/callback`.
  - **Homepage URL** changed to `https://<render-prod-url>`.
- A test push to a connected repo fires the webhook to the prod URL (verify in Render logs).

## Desired output
Sign-in from the prod URL completes the OAuth round-trip. Pushes to a connected repo update the live board on prod.

## Success signals
- Render logs show `POST /api/github/webhook` requests when commits are pushed.
- A sign-in attempt from the prod URL redirects to GitHub, then back to `https://<render>/dashboard`.
- Local dev still works (callback to `localhost:3000` continues to function).

## Failure signals
- `redirect_uri_mismatch` from GitHub on sign-in → callback URL not whitelisted; fix the OAuth App settings.
- Webhook 401s in prod → `GITHUB_APP_WEBHOOK_SECRET` mismatch between Render env and the GitHub App settings.

## Tests
- Manual: sign in from the prod URL, confirm callback succeeds, dashboard loads.
- Manual: push to a connected repo, confirm webhook hits prod and the board updates.
- Manual: sign in from `localhost:3000` (local dev), confirm still works.

## How to test
1. Visit the Render prod URL → click Sign in with GitHub. Expected: redirect to GitHub, authorise the new prod OAuth App, redirect back to `/dashboard` on prod.
2. Push a `hive/` commit to a connected repo. Watch the Render logs — expect `POST /api/github/webhook 200`. Reload `/projects/[id]` in prod, see the board reflect the change.
3. Run `npm run dev` locally, open `localhost:3000`, sign in. Expected: still works (uses the original dev OAuth App credentials in local `.env`).

## Notes
- **Why two OAuth Apps but one GitHub App**: OAuth App callback URL is a single field with no multi-value support. GitHub Apps also have a single webhook URL but only the webhook is environment-specific (settings/installation aren't), so duplicating the whole GitHub App for one URL difference isn't worth it yet. When we want to test webhook flow locally again, we file a follow-up ticket to split into `Bot Hive (Dev)` + `Bot Hive (Prod)` GitHub Apps.
- The webhook secret is the same across dev and prod — both env files point at the same `GITHUB_APP_WEBHOOK_SECRET`. Smee tunnels are now dormant for this app (the GitHub App posts directly to prod).
- Out of scope: custom domain, splitting the GitHub App into dev/prod variants, automating dev/prod credential sync.

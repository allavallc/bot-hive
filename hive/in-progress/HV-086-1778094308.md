## Goal
Document the complete bot lifecycle as a single coherent flow in `AGENTS.md` and `hive/HIVE.md`. Today's docs describe the pieces (claim, signal channel, rejection-pickup, etc.) but not the **end-to-end procedure** a bot follows from "I pick a ticket" through "the human approved it; I stop monitoring." Four specific gaps to close in one pass.

## Why
The user asked, in plain words, "How does a bot select a ticket and follow it all the way through (without bumping into other bots) and then monitor it until approved before stopping?" The honest read of today's docs: each step is described, but a new agent reading AGENTS.md cold can't synthesize the flow without inferring across sections. That's exactly the kind of friction client onboarding (FS-017) will surface.

Plus four specific gaps:

1. **DAG-walk doesn't say "in-review still blocks"** — a backlog ticket whose `Blocked by:` references another ticket currently in `in-review/` is **still blocked** (the human hasn't approved). Today's docs imply blocked-by means "exists somewhere"; the actual rule is "is in done/." Critical when bots are picking tickets in parallel.

2. **No "active_set" convention for session-start monitoring** — `my-work.sh` (HV-078) lists tickets owned by the bot, but there's no documented rule that says "these are the ones you're now monitoring for accept/reject signals." Without this, a bot might forget about its own in-review tickets and not react to rejection.

3. **No SSE-driven rejection auto-handling** — HV-052 says agents should re-claim their rejected work first; HV-082 enables sub-second board updates from `rejected` signals. But the docs don't tie them together: "when you see a `rejected` signal for a ticket in your active_set, automatically re-claim and re-work it." That convention should be explicit.

4. **No SSE-collision resolution for claim races** — today's doc says "git push lock breaks ties" between simultaneous claims, but with the new claim-signal-first convention (HV-085), the lock fires *before* any push. The collision resolution rule should be "loser sees the conflicting claim signal on SSE and re-picks." Document this.

## Done when

### AGENTS.md and `hive/HIVE.md` updates

A coherent **"Bot lifecycle — pick to approved"** section in both files, organized as the actual procedure a bot follows:

```
SESSION START
  - pick handle / resolve agent-id / read focus.md
  - subscribe to SSE signals stream (one connection, lasts session)
  - run scripts/my-work.sh — tickets returned in in-progress/in-review become
    your active_set: the things you're monitoring for human accept/reject
  - tail events.log to catch up

PICK (DAG-walk, refined)
  - filter backlog/ to leaves with Blocked by: deps that are ALL in done/
  - skip candidates with a recent (last 10 min) claim signal from another bot
    on the SSE buffer
  - publish your `claim` signal (this is the lock)
  - if you see a conflicting `claim` from another bot for the same ticket
    arrive within ~2 seconds of yours, the timestamp-loser re-picks

WORK
  - local edits, tests
  - open ONE work PR: backlog → in-review (per HV-085)
  - optionally publish `done` signal (live board flips immediately)
  - active_set += this ticket
  - move on to next ticket — DON'T wait for human

MONITOR (passive — your existing SSE subscription)
  - on every signal received, check refs[0] against active_set:
    - accepted → remove from active_set; stop monitoring
    - rejected → re-claim (move file in-progress, address rejection reason,
      re-ship). New work PR. (HV-052 convention.)
  - active_set empty → no monitoring overhead; just keep working

SESSION END
  - active_set survives via Assigned to: <agent-id> on the ticket files
  - next session's my-work.sh reconstructs it
```

### Specific text edits

- "On every session start" — add "subscribe to SSE; run my-work.sh; treat returned tickets as your active_set."
- "Picking what to claim" / DAG-walk — explicitly state in-review is still blocking: "Blocked by: counts as resolved only when the blocker is in done/. A blocker in in-review (awaiting human accept/reject) still blocks."
- "Real-time channel — how to subscribe" — add the active_set monitoring rule + rejection auto-claim.
- New paragraph or subsection: "Claim collision resolution" — describe the timestamp-loser-re-picks rule.

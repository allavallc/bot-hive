## Goal
Stand up a test harness that exercises multiple Claude agents working concurrently against a shared bot-hive board so we can observe contention, claim conflicts, and SSE fan-out behaviour under real multi-agent load.

## Why
Bot Hive is designed for multi-agent workflows, but all development so far has been single-agent. We need at least one end-to-end run with two or more agents claiming, working, and completing tickets simultaneously before we can trust the git-lock protocol, the SSE broadcast, and the board's merge behaviour under concurrent writes.

## Done when
- At least two agent processes can run concurrently against the same repo and board without silent data loss or phantom ticket state.
- Claim conflicts (non-fast-forward push) are handled gracefully — the losing agent re-selects a different ticket rather than crashing or corrupting state.
- SSE clients connected during the run see all card moves within the 5–10 s latency budget.
- A brief findings doc is appended to `tasks/lessons.md`.

## Desired output
Documented evidence (terminal logs + `git log`) that two agents competed, one won each race, all tickets reached `done/`, and the board stayed consistent throughout.

## Success signals
- No ticket ends up in an inconsistent state (e.g. claimed by two agents, or stuck in `in-progress` with no owner).
- `git log` shows interleaved commits from both agents with correct provenance trailers.
- SSE event count matches ticket-move count with no dropped events.

## Failure signals
- A ticket silently duplicated or lost during concurrent claim.
- An agent swallows a push conflict and overwrites the winner's commit.
- SSE client falls behind and never catches up after a burst.

## Tests
- Run two agent processes against a 5-ticket backlog; confirm all 5 reach `done/` exactly once.
- Deliberately induce a claim conflict (both agents attempt HV-XXX simultaneously) and verify the loser retries on a different ticket.
- Connect an SSE client for the duration and verify event count = ticket-move count.

## Notes
- Out of scope: automated CI integration for multi-agent runs — that's a follow-on ticket once the harness is stable.
- Out of scope: billing / seat tracking for concurrent agents — that's feature-set-003 territory.
- The git-lock protocol (push wins; loser re-pulls and picks again) is the only concurrency primitive — do not add a separate lock service.
